# Function `0x00408000` - WannaCry `ServiceMain` Initialization

## Overview

Function `0x00408000` represents the service entry point used by the sample after the Windows Service Control Manager (SCM) starts the malware as a service.

The function performs the initial service registration and status reporting required for execution under the Windows service model. It:

1. Registers a service control handler at [0x00407F30](0x00407F30.md).
    
2. Initializes a `SERVICE_STATUS` structure in the `.data` section.
    
3. Reports the service state to the Service Control Manager.
    
4. Changes the service state from `SERVICE_START_PENDING` to `SERVICE_RUNNING`.
    
5. Transfers execution to the main service execution path at [0x00407BD0](0x00407BD0.md).
    

The relevant execution flow is:

```text
Windows Service Control Manager
            │
            ▼
       ServiceMain
       0x00408000
            │
            ├── RegisterServiceCtrlHandler
            │        │
            │        └── Handler: 0x00407F30
            │
            ├── SERVICE_STATUS initialization
            │
            ├── SetServiceStatus
            │        │
            │        └── SERVICE_RUNNING
            │
            └── 0x00407BD0
                     │
                     ▼
              Main execution path
```

# 1. Service Entry Point

The function begins with:

```asm
00408000 | 56                       | push esi
00408001 | 33F6                     | xor esi,esi
```

`ESI` is initialized to zero and subsequently used to initialize several fields of the global service-status structure.

The function then prepares the arguments for `RegisterServiceCtrlHandler`:

```asm
00408003 | 68 307F4000              | push 00407F30
00408008 | 68 FC124300              | push 004312FC
```

The string at `0x004312FC` is:

```text
mssecsvc2.0
```

Therefore, the two arguments correspond conceptually to:

RegisterServiceCtrlHandler:

```c
SERVICE_STATUS_HANDLE RegisterServiceCtrlHandlerA(
  LPCSTR  lpServiceName, //Name of the service started by the current thread ("mssecsvc2.0")
  LPHANDLER_FUNCTION lpHandlerProc //Handler function (0x00407F30)
);
```


The sample therefore registers [0x00407F30](0x00407F30.md) as the service control handler associated with the service name `mssecsvc2.0`.

# 2. Initialization of the `SERVICE_STATUS` Structure

Before registering the handler, the function initializes a global structure located at `0x00431430`.

The following instructions populate its fields:

```asm
0040800D | C705 30144300 20000000   | mov dword ptr [431430],20
00408017 | C705 34144300 02000000   | mov dword ptr [431434],2
00408021 | C705 38144300 01000000   | mov dword ptr [431438],1
0040802B | 8935 3C144300            | mov dword ptr [43143C],esi
00408031 | 8935 40144300            | mov dword ptr [431440],esi
00408037 | 8935 44144300            | mov dword ptr [431444],esi
0040803D | 8935 48144300            | mov dword ptr [431448],esi
```

Since `ESI = 0`, the resulting structure is:

```text
Address      Value       Field
------------------------------------------------
0x431430     0x20        dwServiceType
0x431434     0x02        dwCurrentState
0x431438     0x01        dwControlsAccepted
0x43143C     0x00        dwWin32ExitCode
0x431440     0x00        dwServiceSpecificExitCode
0x431444     0x00        dwCheckPoint
0x431448     0x00        dwWaitHint
```

This corresponds to:

```c
SERVICE_STATUS g_Status;

g_Status.dwServiceType             = 0x20;
g_Status.dwCurrentState            = SERVICE_START_PENDING;
g_Status.dwControlsAccepted       = 0x01;
g_Status.dwWin32ExitCode           = 0;
g_Status.dwServiceSpecificExitCode = 0;
g_Status.dwCheckPoint              = 0;
g_Status.dwWaitHint                = 0;
```

The important values are:

```text
0x20 → SERVICE_WIN32_SHARE_PROCESS
0x02 → SERVICE_START_PENDING
0x01 → SERVICE_ACCEPT_STOP
```

Thus, before reporting its status to the SCM, the sample initializes its service status as a Windows service that is currently in the `START_PENDING` state and accepts the stop control.

# 3. Registering the Service Control Handler

The function then calls:

```asm
00408043 | FF15 04A04000 | call dword ptr ds:[<RegisterServiceCtrlHandlerA>]
```

Conceptually:

```c
SERVICE_STATUS_HANDLE hStatus =
    RegisterServiceCtrlHandlerA(
        "mssecsvc2.0",
        0x00407F30
    );
```

`RegisterServiceCtrlHandlerA` associates the service with a control handler.

The handler address is:

```text
0x00407F30
```

This function is responsible for receiving service-control notifications from the SCM.

The returned value is a `SERVICE_STATUS_HANDLE`, which is subsequently stored at:

```asm
0040804B | mov dword ptr ds:[43145C],eax
```

The function therefore preserves the service-status handle globally for subsequent calls to `SetServiceStatus`.

---

# 4. Handling Registration Failure

The return value is checked immediately:

```asm
00408049 | 3BC6                     | cmp eax,esi
0040804B | A3 5C144300              | mov [43145C],eax
00408050 | 74 3A                    | je 0040808C
```

Because `ESI = 0`, the comparison effectively checks:

```c
if (hStatus == NULL)
```

If registration fails, execution jumps directly to:

```text
0x0040808C
```

and the function returns.

If registration succeeds, execution continues with the service status update.

This demonstrates that the sample explicitly verifies whether the SCM accepted the service handler registration.

---

# 5. Transition to `SERVICE_RUNNING`

After successful registration, the function updates the service status structure:

```asm
00408052 | 68 30144300              | push 00431430
00408057 | 50                       | push eax
00408058 | C705 34144300 04000000   | mov [431434],4
00408062 | 8935 44144300            | mov [431444],esi
00408068 | 8935 48144300            | mov [431448],esi
```

The critical change is:

```asm
00408058 | mov dword ptr [431434],4
```

Previously:

```text
dwCurrentState = 2
```

which corresponds to:

```text
SERVICE_START_PENDING
```

It is now changed to:

```text
dwCurrentState = 4
```

which corresponds to:

```text
SERVICE_RUNNING
```

The same structure at `0x431430` is then passed to `SetServiceStatus` together with the previously obtained service-status handle.

Conceptually:

```c
g_Status.dwCurrentState = SERVICE_RUNNING;

SetServiceStatus(
    hStatus,
    &g_Status
);
```

This represents the service initialization transition:

```text
SERVICE_START_PENDING
        │
        │ initialization completed
        ▼
SERVICE_RUNNING
```

---

# 6. `SetServiceStatus`

The function then calls:

```asm
0040806E | FF15 0CA04000 | call dword ptr ds:[<SetServiceStatus>]
```

The arguments are:

```c
SetServiceStatus(
    hStatus,
    &g_Status
);
```

where:

```text
hStatus   = value returned by RegisterServiceCtrlHandlerA
g_Status  = structure at 0x00431430
```

The relationship between the two service APIs is therefore:

```text
RegisterServiceCtrlHandlerA()
            │
            │ returns SERVICE_STATUS_HANDLE
            ▼
       hStatus
            │
            ▼
SetServiceStatus(
    hStatus,
    &SERVICE_STATUS
)
```

The first API establishes the service's association with the SCM and registers the control handler.

The second API uses the resulting service-status handle to report the current state of the service to the SCM.

This is the normal Windows service initialization mechanism, and the sample follows this mechanism before entering its main service execution path.

---

# 7. Service Control Handler

The handler registered by the sample is [0x00407F30](0x00407F30.md):

```text
0x00407F30
```

It is supplied to:

```c
RegisterServiceCtrlHandlerA(
    "mssecsvc2.0",
    0x00407F30
);
```

Consequently, when the SCM sends a supported control notification to the service, the registered handler provides the corresponding callback path.

The important point for the current analysis is that `0x00408000` establishes this relationship:

```text
SCM
 │
 │ service control notification
 ▼
0x00407F30
 │
 └── service-control handling
```

The detailed behavior of `0x00407F30` should therefore be analyzed separately rather than mixing its logic into `ServiceMain`.

---

# 8. Transition Into the Main Service Execution Path

Once the service has been registered and its state has been reported as `SERVICE_RUNNING`, execution proceeds to:

```asm
00408074 | E8 57FBFFFF | call 00407BD0
```

This is the critical transition from service initialization to the main execution logic.

The complete path is therefore:

```text
00408000
   │
   ├── initialize SERVICE_STATUS
   │
   ├── RegisterServiceCtrlHandlerA
   │       │
   │       └── handler = 00407F30
   │
   ├── set state = SERVICE_RUNNING
   │
   ├── SetServiceStatus
   │
   └── call 00407BD0
             │
             ▼
       main service logic
```

Function  [0x00407BD0](0x00407BD0.md) should therefore be considered the beginning of the subsequent execution stage rather than part of the service-registration mechanism itself.

---

# 9. Delay and Process Termination

After returning from `0x00407BD0`, the function executes:

```asm
00408079 | 68 005C2605 | push 05265C00
0040807E | FF15 A4A04000 | call Sleep
```

The value:

```text
0x05265C00
```

is:

```text
86,000,000 ms
```

which corresponds to approximately:

```text
23.89 hours
```

Therefore, if execution returns from `0x00407BD0`, the service enters a very long sleep period.

The function then terminates the process:

```asm
00408084 | 6A 01
00408086 | FF15 68A04000 | call ExitProcess
```

with:

```c
ExitProcess(1);
```

The resulting path is:

```text
00407BD0
    │
    │ returns
    ▼
Sleep(~23.9 hours)
    │
    ▼
ExitProcess(1)
```

For the main service behavior, however, the more important path is the call into `0x00407BD0`, because that is where the sample's substantive execution continues.

# 10. Experimental Methodology

For dynamic analysis, the sample was not allowed to enter the service-control dispatch mechanism normally.

Instead, the instruction pointer was manually redirected to:

```text
0x00408000
```

This allowed the `ServiceMain` logic itself to be examined directly under the debugger.

This distinction is important:

```text
Normal execution:

main
 │
 ▼
StartServiceCtrlDispatcher
 │
 ▼
Service Control Manager
 │
 ▼
ServiceMain
 │
 ▼
00408000
```

During the controlled debugging session:

```text
Debugger
   │
   ▼
EIP = 00408000
   │
   ▼
ServiceMain logic
```

Therefore, the dynamic observations from this function represent the behavior of the service entry routine itself, while the normal SCM dispatch mechanism was bypassed for debugging purposes.

# 11. Relationship With the Earlier Execution Branch

The broader execution architecture identified in the sample is:

```text
Program startup
      │
      ▼
00408090
      │
      │ argc / command-line branch
      │
      ├── normal execution path
      │
      └── service-related path
              │
              ▼
          00408000
              │
              ├── RegisterServiceCtrlHandlerA
              ├── SERVICE_STATUS initialization
              ├── SERVICE_RUNNING
              ├── SetServiceStatus
              │
              ▼
          00407BD0
              │
              ▼
       subsequent execution
```

Thus, `0x00408000` should be interpreted specifically as the **service initialization and ServiceMain stage**, while the substantive network logic begins further down the execution chain.

# 13. Research Report

Function `0x00408000` implements the service-entry initialization stage of the sample.

The function first initializes a global `SERVICE_STATUS` structure with:

```text
dwServiceType       = SERVICE_WIN32_SHARE_PROCESS
dwCurrentState      = SERVICE_START_PENDING
dwControlsAccepted  = SERVICE_ACCEPT_STOP
```

It then registers:

```text
Service name:
mssecsvc2.0

Control handler:
0x00407F30
```

through `RegisterServiceCtrlHandlerA`.

After successful registration, the returned `SERVICE_STATUS_HANDLE` is stored globally and the service state is changed from:

```text
SERVICE_START_PENDING
```

to:

```text
SERVICE_RUNNING
```

The new state is reported to the Service Control Manager through `SetServiceStatus`.

After service initialization is complete, execution transitions to:

```text
0x00407BD0
```

which represents the subsequent main execution path.

The function therefore provides the bridge between the Windows service infrastructure and the sample's own execution logic:

```text
Service Control Manager
        │
        ▼
   ServiceMain
   0x00408000
        │
        ├── Register service handler
        ├── Initialize service status
        ├── Report SERVICE_RUNNING
        │
        ▼
   0x00407BD0
        │
        ▼
 Subsequent malware logic
```

---


From the perspective of the broader WannaCry analysis, this function is therefore the **service initialization boundary**. The following analysis can proceed from [0x00407BD0](0x00407BD0.md), where the service-established execution path transitions into the subsequent malware logic, including the network-related functionality analyzed later in the project.
