## 0x004072A0 - SMB-Based Payload Transfer and Staged Payload Delivery

`0x004072A0` represents a later-stage SMB network routine reached from `0x00407540` only after the preceding SMB processing path returns success.

Unlike the earlier connectivity and protocol-checking routines, this function contains direct evidence of **payload preparation and network transmission**. Most importantly, the data transmitted by this stage can be traced back to the two large in-memory buffers constructed earlier by `0x00407A20`. Those buffers contain embedded PE data together with a copy of the running WannaCry executable.

This establishes a direct data-flow relationship between the previously identified payload blobs and the later SMB transfer stage.

### 1. SMB session establishment

The function first creates a TCP socket and connects to the target on port `445`.

The initial protocol sequence reproduces the SMB1 communication observed in the preceding routines:

```text
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP)
        │
        ▼
connect(target, 445)
        │
        ▼
send(0x0042E544, 0x89)
        │
        └── SMB_COM_NEGOTIATE
        │
        ▼
recv(..., 0x400)
        │
        ▼
send(0x0042E5D0, 0x8C)
        │
        └── SMB_COM_SESSION_SETUP_ANDX
        │
        ▼
recv(..., 0x400)
        │
        ▼
patch 0x0042E65C
        │
        ▼
send(0x0042E65C, 0x60)
        │
        └── SMB_COM_TREE_CONNECT_ANDX
        │
        ▼
recv(..., 0x400)
```

Thus, `0x004072A0` does not operate as an independent application-layer protocol. It first establishes the same SMB session context used by the preceding propagation routines.

The important difference appears after the Tree Connect stage.

---

### 2. Response-dependent transaction stage

After receiving the Tree Connect response, the function extracts several bytes from the response and uses them to modify prebuilt transaction buffers located around:

```text
0x0042E6BC
0x0042E72C
```

The resulting buffer is transmitted with:

```text
send(socket, 0x0042E6BC, 0x52, 0)
```

The function then waits for another response:

```text
recv(socket, ..., 0x1000, 0)
```

A specific response byte is checked:

```text
[ESP+0x4A] == 0x51
```

where:

```text
0x51 = 'Q'
```

Only when this condition is satisfied does execution continue into the payload preparation path.

This is significant because the subsequent code is not executed unconditionally after establishing SMB connectivity. It is gated by a response received from the target.

The observed structure is therefore:

```text
SMB session
    │
    ├── NEGOTIATE
    ├── SESSION_SETUP
    ├── TREE_CONNECT
    └── transaction / control stage
             │
             ▼
         receive response
             │
          byte == 'Q' ?
             │
          yes ▼
       payload stage
```

---

### 3. Response-derived values

After the `'Q'` response is observed, two DWORD values are extracted from the received data:

```text
[ESP+0x3E]
[ESP+0x3A]
```

These values are passed into two helper functions:

```text
0x00406EB0
0x00406ED0
```

Their behavior can be reconstructed sufficiently to establish their role in the following payload-generation stage.

---

### 4. `0x00406EB0` - zero-value validation

[0x00406EB0](0x00406EB0.md) is a simple boolean test.

Its effective behavior is:

```c
int CheckValue(uint32_t value)
{
    return value == 0;
}
```

The function returns:

```text
1 → argument == 0
0 → argument != 0
```

There is no cryptographic operation or complex transformation here. Its purpose is simply to derive a boolean condition from one of the response-derived values.

---

### 5. `0x00406ED0` - DOUBLEPULSAR XOR Key Derivation

[0x00406ED0](0x00406ED0.md) performs a deterministic bitwise transformation of a single DWORD.

The operation includes:

- byte masking,
    
- 16-bit shifts,
    
- byte rearrangement,
    
- left/right shifts,
    
- addition of the original value to itself,
    
- XOR-based mixing.
    

Conceptually:

```text
input DWORD
    │
    ├── byte extraction
    ├── byte/word rearrangement
    ├── shifts
    ├── arithmetic mixing
    └── XOR
         │
         ▼
   transformed DWORD
```

The function should not be classified as a cryptographic hash based on the observed code alone. It is better described as a **custom deterministic bit/byte transformation** whose result is subsequently supplied to the payload preparation routine.

Its importance is therefore not the transformation itself, but its position in the data flow:

```text
SMB response
     │
     ├── response-derived DWORD
     │       │
     │       └── 0x00406ED0
     │                │
     │                ▼
     │         transformed value
     │
     └── response-derived DWORD
             │
             └── 0x00406EB0
                      │
                      ▼
                  boolean
```

Both results are subsequently passed into `0x00406F50`.

## 6. `0x00406F50` - payload buffer construction

[0x00406F50](0x00406F50.md) is the most important helper for establishing the relationship between the SMB communication and the previously reconstructed payload blobs.

The function selects one of two global buffers depending on its mode argument.

### Mode-dependent buffer selection

When the mode argument is non-zero:

```text
ESI = [0x70F864]
EBX = 0x1305
EBP = 0x506000
```

When the mode argument is zero:

```text
ESI = [0x70F868]
EBX = 0x1800
EBP = 0x50D800
```

The two global pointers are exactly the buffers created earlier by `0x00407A20`.

Previously reconstructed state:

```text
0x70F864 → Buffer 1
0x70F868 → Buffer 2
```

Those buffers were constructed as:

```text
Buffer 1
┌───────────────────────────────┐
│ embedded PE blob #1           │
├───────────────────────────────┤
│ DWORD executable file size    │
├───────────────────────────────┤
│ copy of running executable    │
└───────────────────────────────┘

Buffer 2
┌───────────────────────────────┐
│ embedded PE blob #2           │
├───────────────────────────────┤
│ DWORD executable file size    │
├───────────────────────────────┤
│ copy of running executable    │
└───────────────────────────────┘
```

`0x00407A20` created these buffers using `GlobalAlloc`, copied the embedded PE regions into them, obtained the size of the currently running executable, and appended the executable itself.

Therefore, when `0x00406F50` later selects:

```asm
mov esi, [0x70F864]
```

or:

```asm
mov esi, [0x70F868]
```

it is selecting a buffer that has already been populated with actual executable/payload data.

!!**This is the critical link between the earlier static reconstruction and the network propagation stage.**!!

---

## 7. Payload data is copied into a new transfer context

`0x00406F50` allocates another large memory region using `GlobalAlloc(0x40, ...)`.

It then copies data from the selected staged buffer into this newly allocated region.

The relevant data flow is therefore:

```text
Embedded PE blobs
       │
       │ 0x00407A20
       ▼
0x70F864 / 0x70F868
       │
       │ selected by 0x00406F50
       ▼
newly allocated transfer buffer
       │
       │ processed through 0x00406F00
       ▼
network transmission
```

This is considerably stronger evidence than merely observing that the binary contains embedded PE files.

!!**The code demonstrates that these buffers are not only created or stored for later local use: a later network routine explicitly selects them as the source for constructing data that is subsequently transmitted through the socket.**!!

---

## 8. Chunked network transmission

After the transfer context has been prepared, `0x004072A0` enters a loop.

For each iteration it calls:

```text
0x00406F00
```

to construct the next network data block.

The generated data is then transmitted using:

```text
send(socket, buffer, 0x1052, 0)
```

The remote side is subsequently queried with:

```text
recv(socket, ..., 0x1000, 0)
```

The received data is checked for:

```text
0x51 = 'R'
```

Only an `'R'` response causes the transfer loop to advance.

The data pointer is then advanced by:

```text
0x1000
```

and the next chunk is generated.

The resulting transfer pattern is:

```text
                 payload buffer
                      │
                      ▼
                0x00406F00
                      │
                      ▼
             construct next block
                      │
                      ▼
             send(..., 0x1052)
                      │
                      ▼
             recv(..., 0x1000)
                      │
                      ▼
                response == 'R'?
                   /       \
                 yes        no
                  │          │
                  ▼          ▼
             next chunk     exit
```

The repeated `0x1000` advancement strongly indicates that the function is transferring the prepared data in chunks rather than sending the entire staged buffer in a single operation.

The `0x1052` transmission size additionally indicates that the transmitted block contains protocol/framing data in addition to approximately `0x1000` bytes of payload data. The exact internal structure of this framing belongs to `0x00406F00` and is outside the present scope.

---

## 9. Final variable-length transmission

After the chunked transfer loop, the function can construct an additional final packet.

Its transmission length is calculated dynamically:

```text
EBP + 0x52
```

The function again calls:

```text
0x00406F00
```

to construct the corresponding data and then sends it through the same socket.

Therefore the complete transfer consists of:

```text
SMB negotiation
      │
      ▼
SMB session establishment
      │
      ▼
response-dependent control stage
      │
      ▼
'Q' response
      │
      ▼
payload preparation
      │
      ├── chunk 0 ── send 0x1052 ── 'R'
      ├── chunk 1 ── send 0x1052 ── 'R'
      ├── chunk 2 ── send 0x1052 ── 'R'
      ├── ...
      │
      └── final variable-length block
```

# 10. Direct relationship to the embedded payloads

The most significant finding of this function is the following data-flow chain:

```text
                 STATIC / INITIAL STAGE
                 ======================

0x0040B020
embedded PE blob #1
      │
      │
      └──────────────┐
                     ▼
                0x00407A20
                     │
                     ▼
                 0x70F864
                 Buffer 1
                     │
                     │
                     │
0x0040F080            │
embedded PE blob #2   │
      │               │
      └──────────────┐ │
                     ▼ ▼
                0x00407A20
                     │
                     ▼
                 0x70F868
                 Buffer 2


                 LATER NETWORK STAGE
                 ===================

             0x004072A0
                   │
                   ▼
             0x00406F50
                   │
          selects Buffer 1/2
                   │
                   ▼
          copies staged data
                   │
                   ▼
             0x00406F00
                   │
                   ▼
             send(socket,...)
                   │
                   ▼
             remote target
```

This is the strongest evidence obtained so far for the purpose of establishing the role of the previously discovered blobs.

The important point is that the conclusion does not depend on an assumption about the contents of the protocol.

We have independently established:

1. The binary contains two embedded PE regions.
    
2. `0x00407A20` copies those regions into dedicated global buffers.
    
3. The same function appends the running executable to those buffers.
    
4. `0x00406F50`, reached from `0x004072A0`, explicitly selects one of those global buffers.
    
5. `0x00406F50` copies data from the selected buffer into a newly allocated transfer context.
    
6. `0x00406F00` subsequently generates transmission blocks from that context.
    
7. `0x004072A0` sends those blocks through the established SMB socket.
    
8. The remote side acknowledges individual chunks with the expected `'R'` response.
    

This provides direct static evidence that the previously prepared PE/self-image data participates in the network transfer stage.

# 11. Role in the propagation architecture

Within the reconstructed propagation chain, `0x004072A0` can therefore be placed as follows:

```text
0x00409160
    │
    │ enumerate local network
    ▼
0x00407720
    │
    │ distribute target IPs
    ▼
0x004076B0
    │
    │ TCP/445 connectivity gate
    ▼
0x00407540
    │
    ├── 0x00401980
    │      SMB negotiation / initial protocol stage
    │
    ├── 0x00401B70
    │      SMB exploitation / target-state processing
    │
    └── 0x004072A0
           │
           │ later SMB payload stage
           │
           ├── response-dependent control exchange
           │
           ├── 0x00406EB0
           │      response-value validation
           │
           ├── 0x00406ED0
           │      response-value transformation
           │
           ├── 0x00406F50
           │      select and prepare staged payload
           │
           └── 0x00406F00
                  │
                  │ construct transfer blocks
                  ▼
               send()
                  │
                  ▼
             remote target
```

The important architectural transition is:

```text
0x00401B70
    target-state / exploitation-related SMB processing
                  │
                  ▼
0x004072A0
    payload transfer
```

Thus, `0x004072A0` should not be described merely as "another SMB request sequence". Its defining characteristic is that it bridges the **previously constructed payload buffers** and the **network transmission stage**.

## Research Report

`0x004072A0` provides the strongest evidence so far that the WannaCry sample's embedded PE data is intended for remote propagation.

The function establishes an SMB connection, performs the required protocol exchange, waits for a response-dependent condition (`'Q'`), and then invokes `0x00406F50`. That helper explicitly selects one of the two global buffers populated by `0x00407A20` with embedded PE data and a copy of the running executable. The selected data is copied into a new transfer context and subsequently processed into network blocks by `0x00406F00`.

The resulting blocks are transmitted through the SMB connection in repeated `0x1052`-byte sends, with `0x1000`-byte responses and an `'R'` acknowledgement controlling progression, followed by a final variable-length transfer.

Therefore, even though the complete remote execution stage cannot be dynamically reconstructed in the present environment, the local binary contains a clear and traceable path from **embedded payload blobs → staged memory buffers → payload preparation → network transmission**.

This provides direct static evidence that the previously identified embedded PE blobs are part of the malware's remote propagation payload rather than unrelated embedded data.
