## 0x00406F50 - Payload Preparation and Chunked Transfer Construction

`0x00406F50` is a large helper responsible for preparing staged payload data for subsequent network transmission.

The function is reached from `0x004072A0` after the SMB transaction stage has produced the expected response marker. Its operation can be divided into several stages:

1. creation of a large stack frame;
    
2. initialization of local working buffers;
    
3. selection of one of the two previously prepared payload buffers;
    
4. allocation of a new transfer buffer;
    
5. copying payload-related data into the allocated buffer;
    
6. preparation of a transfer context;
    
7. transformation of data through `0x00406F00`;
    
8. construction and transmission of fixed-size chunks;
    
9. processing of remote acknowledgements;
    
10. transmission of a final variable-length block;
    
11. cleanup of the allocated transfer buffer.
    

The most important relationship is between this function and the buffers created earlier by [0x00407A20](0x00407A20.md) .

---

### 1. Large stack frame initialization

The function begins with:

```asm
00406F50  mov eax,20E4
00406F55  call 409860
00406F5A  push ebx
00406F5B  push ebp
00406F5C  push esi
00406F5D  push edi
```

`0x20E4` is passed to [0x00409860](0x00409860.md) .

The helper at `0x00409860` is a compiler/runtime stack-probing routine. It moves the stack pointer through page-sized regions (`0x1000` bytes) and touches the corresponding memory pages before the large stack frame is established.

The function therefore reserves approximately:

```text
0x20E4 bytes ≈ 8.2 KB
```

of stack space.

`0x00409860` is not part of the malware's payload protocol. It is used to safely establish the large local stack frame required by `0x00406F50`.

---

### 2. Initialization of local working buffers

After establishing the stack frame, `0x00406F50` initializes two large local regions.

The first region starts around:

```text
[ESP+0x2C]
```

and is initialized to zero using:

```asm
mov ecx,431
xor eax,eax
lea edi,[esp+2D]
mov byte ptr [esp+2C],0
rep stosd
stosw
stosb
```

The effective operation is a large zero-initialization of a local buffer.

A second region starts around:

```text
[ESP+0x10F4]
```

and is similarly zeroed:

```asm
mov ecx,3FF
xor eax,eax
lea edi,[esp+10F5]
mov byte ptr [esp+10F4],0
rep stosd
stosw
stosb
```

This second region is approximately `0x1000` bytes and is later used as a receive buffer.

The function also initializes several small local fields around:

```text
[ESP+0x10]
[ESP+0x14]
[ESP+0x18]
[ESP+0x1C]
```

These fields form part of the working transfer state used by the later packet-building code.

---

### 3. Selection of the staged payload buffer

The next branch is one of the most important parts of the function:

```asm
00406FAA  mov eax,[esp+20FC]
00406FBA  test eax,eax
00406FBC  je 406FD4
```

The value at `[ESP+0x20FC]` determines which previously prepared payload buffer is selected.

#### Non-zero mode

```asm
00406FC2  mov esi,[70F864]
00406FC8  mov ebx,1305
00406FCD  mov ebp,506000
```

This selects:

```text
ESI = [0x70F864]
```

which is the first global payload buffer created by `0x00407A20`.

The associated parameters are:

```text
EBX = 0x1305
EBP = 0x506000
```

#### Zero mode

```asm
00406FD4  mov esi,[70F868]
00406FDA  mov ebx,1800
00406FDF  mov ebp,50D800
```

This selects:

```text
ESI = [0x70F868]
```

which is the second global payload buffer created by `0x00407A20`.

The associated parameters are:

```text
EBX = 0x1800
EBP = 0x50D800
```

Therefore:

```text
             0x00406F50
                  │
          mode argument
             /       \
            /         \
      non-zero         zero
         │               │
         ▼               ▼
 [0x70F864]          [0x70F868]
 Buffer 1             Buffer 2
         │               │
      0x1305           0x1800
      0x506000         0x50D800
```

This is the first direct connection between `0x00406F50` and the staged buffers produced by `0x00407A20`.

---

### 4. Allocation of a new transfer buffer

The function calculates:

```asm
00406FE4  lea edx,[ebx+ebp+0C]
00406FE8  push edx
00406FE9  push 40
00406FEB  call [GlobalAlloc]
```

The requested allocation size is:

```text
EBX + EBP + 0x0C
```

and the allocation flag is:

```text
0x40 = GMEM_ZEROINIT
```

The returned pointer is stored at:

```text
[ESP+0x20]
```

This allocated region becomes the working memory area used to construct the subsequent transfer data.

If allocation fails, execution jumps to the cleanup path.

---

### 5. Copying data from the selected payload region

The function then performs a bulk memory copy:

```asm
00406FFD  mov ecx,ebp
00406FFF  lea edi,[ebx+eax]
00407002  mov edx,ecx
00407004  shr ecx,2
00407007  rep movsd
00407009  mov ecx,edx
0040700B  and ecx,3
0040700E  rep movsb
```

The selected source region is copied into the newly allocated buffer.

The destination begins at:

```text
allocated_buffer + EBX
```

while the copy length is controlled by `EBP`.

Thus the allocated region can be represented conceptually as:

```text
allocated buffer
┌──────────────────────────────────────┐
│                                      │
│     EBX-byte prefix / working area   │
│                                      │
├──────────────────────────────────────┤ ← +EBX
│                                      │
│       copied staged data              │
│       length = EBP                    │
│                                      │
├──────────────────────────────────────┤
│ additional working space             │
└──────────────────────────────────────┘
```

The exact semantic boundaries of the individual fields depend on the data consumed by [0x00406F00](0x00406F00.md), but the important point is that data from the selected staged buffer is copied into a newly allocated working region.

---

### 6. Alignment and transfer-size calculation

The code at `0x00407010` derives an aligned value from:

```text
EBX + EBP
```

and stores the result in:

```text
[ESP+0x1C]
```

The calculation uses division by four and rounding behavior to derive a DWORD-oriented size/offset.

This value is later passed to `0x00406F00` as part of the data transformation stage.

The function subsequently retrieves the mode value again:

```asm
00407044  mov ecx,[esp+20FC]
0040704B  test ecx,ecx
```

and initializes different global pointers depending on the selected payload buffer.

---

### 7. Mode-dependent transfer context

For the non-zero mode:

```asm
0040704F  lea ecx,[ebp+0D70]
00407055  mov esi,42E758
0040705A  mov [42ECE9],ecx
00407060  mov [42E750+ebx],ebp
00407066  mov [42E754+ebx],1
```

For the zero mode:

```asm
00407074  lea ecx,[ebp+0F8A]
0040707A  mov esi,42FA60
0040707F  mov [4302CE],ecx
00407085  mov [42FA58+ebx],ebp
0040708B  mov [42FA5C+ebx],1
```

These assignments establish pointers and state values used by the subsequent transfer construction.

At this point the function has therefore:

```text
1. selected one staged payload buffer;
2. selected its associated size/offset parameters;
3. allocated a new working buffer;
4. copied staged data into it;
5. initialized global transfer state.
```

---

### 8. First call to `0x00406F00`

The function then calls:

```asm
004070AE  mov ecx,[esp+1C]
004070B2  push ecx
004070B3  push eax
004070B4  push edx
004070B5  call 406F00
```

[0x00406F00](0x00406F00.md) operates on a buffer in-place using a repeating four-byte XOR operation.

Its core loop is:

```asm
mov dl,[key + (index & 3)]
mov bl,[buffer + index]
xor bl,dl
mov [buffer + index],bl
```

Equivalent pseudocode:

```c
for (i = 0; i < length; i++)
    buffer[i] ^= key[i & 3];
```

Therefore the data prepared by `0x00406F50` is transformed using a repeating four-byte XOR key.

Because XOR is symmetric, this operation alone doesnt establish whether the data is being encoded or decoded. The safe conclusion is that `0x00406F00` performs an in-place four-byte repeating XOR transformation.

---

## 9. Calculation of the chunk count

After the initial transformation, the function calculates how many full `0x1000`-byte chunks are required:

```asm
004070C1  mov eax,ebp
004070C3  cdq
004070C4  and edx,FFF
004070CA  add eax,edx
004070CC  mov ebx,eax
004070CE  sar ebx,C
```

This effectively derives a rounded-up division by `0x1000`.

Conceptually:

```c
chunk_count = (payload_size + 0xFFF) >> 12;
```

The remaining size is also derived and retained in `EBP` for the final transfer stage.

Thus the function separates the staged data into:

```text
full 0x1000-byte chunks
+
remaining tail
```

---

# 10. Construction of the per-chunk packet

The function initializes a packet template from:

```text
0x0042E710
```

using:

```asm
mov ecx,11
mov esi,42E710
lea edi,[esp+2C]
rep movsd
movsw
```

This copies the predefined packet header/template into the local working buffer.

The function then enters the chunk loop.

The loop index is stored at:

```text
[ESP+0x28]
```

and the current data offset is stored at:

```text
[ESP+0x24]
```

Initially both are zero.

---

## 11. Per-chunk data preparation

Each iteration begins at `0x00407107`.

The current chunk index and current data offset are loaded:

```asm
00407107  mov esi,[esp+24]
0040710B  mov eax,[esp+1C]
0040710F  mov edx,[esp+2100]
```

A `0x1000`-byte block size is explicitly established:

```asm
0040711E  push 0C
00407120  mov eax,1000
```

The function then calls `0x00406F00` again:

```asm
0040712F  call 406F00
```

This prepares the current chunk using the same four-byte repeating XOR transformation.

The resulting data is then copied into the local network packet buffer.

---

# 12. Transmission of each chunk

The resulting packet is transmitted using:

```asm
0040716D  push 0
00407173  push 1052
00407178  push ecx
00407179  push esi
0040717A  call send
```

Therefore:

```text
socket  = current SMB socket
buffer  = local packet buffer
length  = 0x1052
flags   = 0
```

The important observation is that the function doesnt transmit the staged payload buffer directly with `send()`.

Instead:

```text
staged payload
      │
      ▼
working buffer
      │
      ▼
0x00406F00
      │
      ▼
transformed chunk
      │
      ▼
SMB/application packet template
      │
      ▼
send(..., 0x1052)
```

This is why `0x00406F00` is important: it is part of the transformation performed immediately before the data is incorporated into the transmitted block.

---

# 13. Remote acknowledgement

After every chunk transmission, the function waits for a response:

```asm
00407184  push 0
0040718D  push 1000
00407192  push edx
00407193  push esi
00407194  call recv
```

The receive buffer is up to `0x1000` bytes.

The function then checks:

```asm
0040719E  cmp byte ptr [esp+1116],52
```

where:

```text
0x52 = 'R'
```

Therefore the transfer continues only if the expected response marker is received.

If the response is not `'R'`, the loop terminates.

When `'R'` is received:

```asm
004071A8  mov eax,[esp+28]
004071AC  mov edx,[esp+24]
004071B0  inc eax
004071B1  add edx,1000
```

the function:

```text
increments chunk index
advances source offset by 0x1000
```

and starts the next iteration.

The complete chunk-transfer protocol is therefore:

```text
construct chunk
      │
      ▼
send 0x1052 bytes
      │
      ▼
recv up to 0x1000 bytes
      │
      ▼
response byte == 'R'?
      │
   yes│
      ▼
advance by 0x1000
      │
      └──────────► next chunk
```

This is strong evidence of a **chunked, acknowledgement-driven transfer mechanism**.

---

# 14. Final partial block

After all full `0x1000`-byte chunks have been processed, the function checks:

```asm
004071C7  test ebp,ebp
004071C9  jle 407287
```

If a remaining amount exists, a final variable-length packet is constructed.

The code first calculates:

```asm
004071CF  lea eax,[ebp+4E]
004071D3  call htons
```

and places the resulting network-order value into the packet.

The function then prepares another call to `0x00406F00`.

The final transmitted length is:

```asm
00407250  add ebp,52
```

giving:

```text
final_send_size = remaining_data + 0x52
```

The transformed data is copied into the packet buffer and transmitted:

```asm
00407256  push 0
00407265  push ebp
00407266  push ecx
00407267  push esi
00407268  call send
```

Thus the transfer consists of:

```text
[0x1000-byte chunk + protocol framing] × N
                         +
              [final partial chunk + framing]
```

---

# 15. Cleanup

After the final transmission, the allocated working buffer is released:

```asm
00407287  mov eax,[esp+20]
0040728B  push eax
0040728C  call [GlobalFree]
```

The saved registers and large stack frame are then restored:

```asm
pop edi
pop esi
pop ebp
xor eax,eax
pop ebx
add esp,20E4
ret
```

The function returns `0` after completing or terminating the transfer path.

---

# 16. `0x00406F00` - Repeating XOR Transformation

`0x00406F00` is called multiple times by `0x00406F50` during payload preparation.

Its core loop is:

```asm
00406F1F  mov edx,eax
00406F21  and edx,80000003
...
00406F2E  mov dl,[esp+edx+8]

00406F32  mov bl,[eax+ecx]
00406F35  xor bl,dl
00406F37  mov [eax+ecx],bl

00406F3A  inc eax
00406F3B  cmp eax,esi
00406F3D  jl 406F1F
```

For the normal positive index range, the key index reduces to:

```text
index & 3
```

resulting in a four-byte repeating key:

```text
K0 K1 K2 K3 K0 K1 K2 K3 ...
```

The effective transformation is:

```c
for (i = 0; i < length; i++)
    buffer[i] ^= key[i & 3];
```

The operation is performed in-place.

No cryptographic primitive is involved in the observed implementation. It is a simple repeating XOR transformation.

Because XOR is reversible:

```text
encoded = data ^ key
decoded = encoded ^ key
```

the assembly alone doesnt establish whether the routine is being used for encoding or decoding. Its observed role here is to transform data immediately before it is incorporated into the transfer packet.

# 17. Relationship between the three functions

The three relevant functions can therefore be understood as follows:

```text
0x00409860
    │
    └── compiler-generated stack probing
            │
            ▼
       0x00406F50
            │
            ├── select [0x70F864] / [0x70F868]
            │
            ├── allocate transfer buffer
            │
            ├── copy staged payload data
            │
            ├── calculate transfer layout
            │
            ├── call 0x00406F00
            │       │
            │       └── repeating 4-byte XOR
            │
            ├── build chunk packet
            │
            ├── call 0x00406F00
            │
            ├── send 0x1052
            │
            ├── recv 0x1000
            │
            ├── require 'R'
            │
            ├── repeat for next 0x1000-byte chunk
            │
            ├── process remaining tail
            │
            ├── call 0x00406F00
            │
            ├── send final variable-length block
            │
            └── GlobalFree
```

The important architectural relationship is:

```text
0x00407A20
     │
     │ creates payload buffers
     ▼
0x70F864 / 0x70F868
     │
     │ selected by
     ▼
0x00406F50
     │
     │ prepares transfer data
     ▼
0x00406F00
     │
     │ 4-byte repeating XOR
     ▼
network packet construction
     │
     ▼
send()
```

This gives a concrete data-flow connection between the PE blobs identified earlier and the network transfer code.

## 18. Significance for the WannaCry propagation chain

The importance of `0x00406F50` is therefore not a single `send()` call. Its significance comes from the complete sequence:

```text
embedded PE data
      ↓
0x00407A20
      ↓
0x70F864 / 0x70F868
      ↓
0x00406F50
      ↓
newly allocated transfer buffer
      ↓
0x00406F00
      ↓
repeating XOR transformation
      ↓
packet construction
      ↓
0x1052-byte network transmission
      ↓
remote 'R' acknowledgement
      ↓
next payload chunk
```

The code provides direct evidence that the previously identified embedded executable data is incorporated into a later network transfer mechanism.

The exact remote-side interpretation of the transmitted data cannot be recovered solely from this local function. However, the local data flow is unambiguous: the buffers containing the embedded PE material are selected by `0x00406F50`, copied into a transfer context, transformed, incorporated into packets, and transmitted through the network socket.

This makes `0x00406F50` a key bridge between the **payload construction stage** and the **SMB-based network propagation stage**.
