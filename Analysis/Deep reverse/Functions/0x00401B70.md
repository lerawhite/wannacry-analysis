##  `0x00401B70` - SMB Transaction2 Propagation Stage

`0x00401B70` implements a separate SMB1 communication sequence against the target host. Unlike `0x00401980`, which performs the earlier SMB negotiation and transaction sequence, this function creates a new TCP connection to port `445` and establishes its own SMB session.

The target IP is supplied as a string and converted with `inet_addr()`. The destination port is converted with `htons()`, followed by:

```text
socket(AF_INET, SOCK_STREAM, 0)
connect(target, 445)
```

If the connection or any subsequent network operation fails, the socket is closed and the function returns `0`. A successful completion of the required exchange results in `EAX = 1`.

### SMB Negotiation

The first request is an `SMB_COM_NEGOTIATE (0x72)` packet located at `0x0042E544`. The dialect list includes:

```text
PC NETWORK PROGRAM 1.0
LANMAN1.0
Windows for Workgroups 3.1a
LM1.2X002
LANMAN2.1
NT LM 0.12
```

The target returns an 0x85-byte SMB response, confirming that the SMB1 negotiation stage is processed by the remote endpoint.

### IPC$ Tree Connection

The next request is `SMB_COM_TREE_CONNECT_ANDX (0x75)`, using the buffer at `0x0042E65C`.

The request contains the UNC path:

```text
\\192.168.56.20\IPC$
```

This establishes the intended transition from the SMB session to the IPC$ tree.

### SMB_COM_TRANSACTION2

Despite the failed receive, the static code path prepares another SMB packet at `0x0042E6BC`:

```text
00 00 00 4E
FF 53 4D 42
32
```

The command byte `0x32` identifies `SMB_COM_TRANSACTION2`. Microsoft documents `SMB_COM_TRANSACTION2` as a transaction mechanism carrying operation-specific setup, parameter, and data fields; the server response may likewise contain transaction parameters and data.

Before sending this request, the function copies selected bytes from its receive buffer into the transaction template:

```text
recv buffer +0x00 → 0x0042E6D8
recv buffer +0x01 → 0x0042E6D9
recv buffer +0x04 → 0x0042E6DC
recv buffer +0x05 → 0x0042E6DD
```

Because the preceding `recv()` failed, these values cannot be treated as observed server response data. They represent fields that the function is statically prepared to derive from the preceding exchange.

The resulting packet is then sent and another `recv()` is performed. The received data is subsequently checked for a specific byte value:

```asm
cmp byte ptr [esp+42], 0x51
```

where `0x51` corresponds to ASCII `Q`.

If the expected response condition is met, the function modifies additional fields in the same transaction template and performs another `send()` / `recv()` exchange.

### Observed and Statically Reconstructed Behaviour

The complete sequence can therefore be reconstructed as:

```text
TCP connection to target:445
        │
        ▼
SMB_COM_NEGOTIATE
        │
        ▼
SMB_COM_SESSION_SETUP_ANDX
        │
        └── STATUS_ACCESS_DENIED
        │
        ▼
SMB_COM_TREE_CONNECT_ANDX
        │
        └── \\TARGET\IPC$
        │
        ▼
recv() failure in controlled execution
        │
        ▼
SMB_COM_TRANSACTION2
        │
        ▼
response-dependent processing
        │
        ├── check received byte == 0x51 ('Q')
        │
        └── additional transaction exchange
```

---

This function therefore represents a substantially later SMB communication stage than the initial connectivity and negotiation logic. Its use of `SMB_COM_TRANSACTION2`, response-dependent field construction, and subsequent conditional exchange is consistent with the broader SMB propagation workflow implemented by WannaCry. Independent technical analysis of WannaCry has likewise documented an SMB propagation sequence involving TCP/445, IPC$, SMB transactions, and subsequent MS17-010-related processing.

However, the exact remote-side operation and exploitation result were **not dynamically reproduced** in this analysis. The controlled execution terminated at the failed Tree Connect response, so the later `SMB_COM_TRANSACTION2` exchange and its server response remain statically reconstructed rather than directly observed.

### Research report  

`0x00401B70` can be characterized as an SMB1 transaction-stage routine that:

1. creates a new TCP connection to port `445`;
    
2. performs SMB1 negotiation;
    
3. performs Session Setup;
    
4. connects to the `IPC$` tree;
    
5. prepares and sends an `SMB_COM_TRANSACTION2` request;
    
6. evaluates the subsequent response and conditionally performs another transaction exchange;
    
7. returns success only after the required communication sequence completes.
    

The function is therefore a key component of the per-target SMB propagation workflow invoked from `0x00407540`.
