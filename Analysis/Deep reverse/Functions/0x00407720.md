## Function `0x00407720` - Worker Dispatcher and IPv4 Target Distribution

### Overview

Function `0x00407720` acts as the worker dispatcher for the IPv4 target collection generated by `0x00409160`.

Its main responsibilities are:

1. Receive the dynamically constructed IPv4 array from `0x00409160`.
    
2. Validate that the array exists and determine its number of elements.
    
3. Iterate through the IPv4 values sequentially.
    
4. Limit worker creation using a shared counter.
    
5. Create a worker thread at `0x004076B0` for each target.
    
6. Pass the IPv4 value itself as the worker argument.
    
7. **Atomically** increment the shared worker counter.
    
8. Introduce a short delay before processing the next target.
    

The function doesnt perform the actual network communication itself. It distributes target addresses to `0x004076B0`, where the subsequent network processing takes place.

---

### Initial SEH Setup and Local State

The function begins by installing a Structured Exception Handling frame:

```asm
00407720 | 6A FF                    | push FFFFFFFF
00407722 | 68 C09B4000              | push 0x00409BC0
00407727 | 64:A1 00000000           | mov eax, fs:[0]
0040772D | 50                       | push eax
0040772E | 64:8925 00000000         | mov fs:[0], esp
```

The handler at `0x00409BC0` is consistent with compiler-generated MSVC exception handling. The observed setup therefore appears to be part of the compiler-generated function frame **rather** than a **malware-specific** exception mechanism.

Several stack-based variables are then initialized to zero. These variables are subsequently used as the boundaries and state of the IPv4 address collection.

The function then calls:

```asm
00407779 | call 0x00409160
```

The previously analyzed `0x00409160` is responsible for constructing the IPv4 target collection.

## IPv4 Address Collection

Function [0x00409160](0x00409160.md) produces a dynamically allocated array containing 32-bit IPv4 addresses derived from the local network configuration.

IPv4 array extracted dump form x64dbg - [0x00407720_dump_array(ip)_made_by_0x00409160](0x00407720_dump_array(ip)_made_by_0x00409160.txt) .

The two important values received by `0x00407720` are:

```text
local_18 → beginning of array
local_14 → end of array
```

The number of elements is calculated from the distance between these two pointers:

```c
element_count = (array_end - array_begin) / sizeof(uint32_t);
```

Since each IPv4 address occupies one `DWORD`, the pointer difference is shifted right by two:

```asm
sub ecx, eax
sar ecx, 2
```

Runtime analysis confirmed the interpretation of this structure.

The array was observed at:

```text
0x00FB2800
```

and contained:

```text
C0 A8 7C 01
C0 A8 7C 02
C0 A8 7C 03
C0 A8 7C 04
...
C0 A8 7C FE
```

corresponding to:

```text
192.168.124.1
192.168.124.2
192.168.124.3
192.168.124.4
...
192.168.124.254
```

Thus, in the observed environment, the generated collection represented the **host addresses** of the local `/24` network.

## Worker Iteration

After [0x00409160](0x00409160.md) returns, `0x00407720` iterates over the generated collection.

The loop is controlled by two separate conditions:

```asm
0040778F | mov eax,[esp+28]
00407793 | cmp eax,esi
00407795 | je  0x004077FA

00407797 | mov ecx,[esp+2C]
0040779B | sub ecx,eax
0040779D | sar ecx,2
004077A0 | cmp edi,ecx
004077A2 | jae 0x004077FA
```

### 1. Array existence check

The first condition verifies that the beginning pointer is non-zero:

```c
if (array_begin == NULL)
    terminate;
```

This prevents the dispatcher from attempting to process a missing address collection.

In the observed execution, the pointer is non-zero, confirming that `0x00409160` successfully produced the collection.

### 2. Array boundary check

The second condition calculates the number of elements:

```c
element_count =
    (array_end - array_begin) / sizeof(uint32_t);
```

and compares the current iteration index against that value:

```c
if (index >= element_count)
    terminate;
```

Therefore, the loop continues only while there are valid unprocessed elements in the array.

Conceptually:

```c
for (
    index = 0;
    array_begin != NULL &&
    index < ((array_end - array_begin) / sizeof(uint32_t));
    index++
)
{
    ...
}
```

The two conditions therefore establish:

```text
                 array_begin != NULL
                         │
                         ▼
                 valid collection
                         │
                         ▼
              index < element_count
                         │
                         ▼
                valid array element
                         │
                         ▼
                  create worker
```

The second condition is *particularly important* because the array is dynamically sized. The dispatcher doesnt use a hard-coded number of iterations; it derives the number of available IPv4 values from the array boundaries.

## IPv4 Target Extraction

For each valid iteration, the current IPv4 value is loaded using:

```asm
004077C3 | mov edx,[eax+edi*4]
```

where:

```text
EAX = array_begin
EDI = current index
```

Therefore:

```text
array[index]
      │
      ▼
DWORD IPv4 value
      │
      ▼
EDX
```

The value is then passed directly to `_beginthreadex`:

```asm
004077CA | push edx
004077CB | push 0x004076B0
...
004077D4 | call _beginthreadex
```

The worker therefore receives the **IPv4 value itself**, not a pointer to the array element.

Runtime analysis confirmed this relationship.

For example:

```text
Array memory:
C0 A8 7C 01

IPv4:
192.168.124.1

DWORD representation passed to worker:
0x017CA8C0
```

Therefore:

```text
array[0]
    │
    └── 192.168.124.1
            │
            ▼
      0x017CA8C0
            │
            ▼
    _beginthreadex(...)
            │
            ▼
      0x004076B0
```

This provides direct runtime confirmation that the worker argument is the IPv4 value stored in the collection.

## Worker Creation and Concurrency Control

Before creating each worker, the dispatcher checks the global variable:

```text
0x0070F86C
```

This variable acts as a shared worker counter.

The relevant logic is:

```asm
004077A4 | mov ecx,[0x0070F86C]
004077AA | mov esi,0x0A
004077AF | cmp ecx,esi
004077B1 | jle 0x004077C3
```

If the counter is greater than `10`, the dispatcher waits:

```asm
004077B3 | push 64
004077B5 | call Sleep
004077B7 | cmp [0x0070F86C],esi
004077BD | jg  0x004077B3
```

This corresponds to:

```c
while (worker_count > 10)
    Sleep(100);
```

The important point is that the dispatcher doesnt continue creating workers while the shared counter remains above the observed threshold.

Once the counter is `10` or lower, the next target is processed.

---

## Worker Creation

The worker is created with:

```text
Thread entry point:
0x004076B0

Thread argument:
IPv4 value from array[index]
```

Conceptually:

```c
HANDLE hThread = _beginthreadex(
    NULL,
    0,
    0x004076B0,
    target_ip,
    0,
    NULL
);
```

If thread creation succeeds, the returned handle is stored in `ESI`:

```asm
004077D8 | mov esi,eax
004077DB | test esi,esi
004077DD | je 0x004077F1
```

The global counter is then atomically incremented:

```asm
004077DF | push 0x0070F86C
004077E4 | call InterlockedIncrement
```

This indicates that the counter is shared between concurrently executing threads and requires an atomic update.

The thread handle is subsequently closed:

```asm
004077EA | push esi
004077EB | call CloseHandle
```

The worker itself continues executing independently.

---

## Inter-Worker Delay

After the worker creation attempt, the dispatcher performs:

```asm
004077F1 | push 0x32
004077F3 | call Sleep
004077F5 | inc edi
```

`0x32` is `50` milliseconds.

Therefore, after each iteration, the dispatcher waits approximately:

```text
Sleep(50 ms)
```

before processing the next array element.

The resulting worker scheduling logic is:

```text
             worker_count > 10?
                    │
            ┌───────┴───────┐
           YES              NO
            │                │
       Sleep(100)            ▼
            │          load array[index]
            │                │
            └───────◄────────┘
                             │
                             ▼
                    create worker
                    entry = 0x004076B0
                    arg   = target IP
                             │
                             ▼
                 InterlockedIncrement
                             │
                             ▼
                       CloseHandle
                             │
                             ▼
                       Sleep(50 ms)
                             │
                             ▼
                         index++
```

The function therefore implements **worker-count-based throttling combined with a fixed delay between worker creation attempts**.

The observed counter logic shouldt be described as an absolute guarantee that exactly ten workers can exist simultaneously. The counter is incremented here, while its decrement/cleanup occurs elsewhere. The precise conclusion from this function is that worker creation is throttled while the shared counter remains above `10`.

## Relationship with `0x00409160`

The combined behavior of `0x00409160` and `0x00407720` can now be reconstructed:

```text
0x00409160
      │
      │ local adapter/network configuration
      ▼
network range calculation
      │
      ▼
IPv4 address generation
      │
      ▼
filtering / validation / sorting / deduplication
      │
      ▼
DWORD IPv4 array
      │
      │ 192.168.124.1 ... 192.168.124.254
      ▼
0x00407720
      │
      ├── validate array
      │
      ├── calculate element count
      │
      ├── iterate array
      │
      ├── extract IPv4 value
      │
      ├── throttle worker creation
      │
      └── create 0x004076B0
                  │
                  └── target IP as argument
```

This establishes a clear division of responsibility:

```text
0x00409160
    = target collection construction

0x00407720
    = target distribution and worker scheduling

0x004076B0
    = processing of an individual target
```

The actual network operation is therefore not implemented by `0x00407720`; it is delegated to the worker at `0x004076B0`.

## Controlled Target Selection

The generated collection contained the host addresses of the observed local `/24` network:

```text

...
192.168.124.254
```

For the subsequent dynamic analysis, `192.168.124.128` `was selected` from this collection as the *controlled analysis target.*

This address corresponds to the Windows 10 analysis VM and was therefore used to observe the behavior of the worker against a known host rather than attempting to analyze the network behavior of every generated candidate.

The experimental target was configured with **SMB available** over TCP port `445`, which allowed the later analysis of the SMB-related execution path.

The distinction between the generated collection and the selected analysis target is important:


`192.168.124.128` was subsequently used for tracing the worker's network behavior because it was the controlled host configured to provide the SMB service required for the next stage of analysis.

## Functional Reconstruction

The observed behavior can be represented by the following pseudocode:

```c
void WorkerDispatcher(void)
{
    uint32_t *array_begin;
    uint32_t *array_end;

    // Populate IPv4 target collection
    BuildTargetArray(&array_begin, &array_end);

    if (array_begin == NULL)
        goto cleanup;

    size_t element_count =
        (array_end - array_begin);

    for (size_t index = 0;
         index < element_count;
         index++)
    {
        while (worker_count > 10)
            Sleep(100);

        uint32_t target_ip = array_begin[index];

        HANDLE hThread = _beginthreadex(
            NULL,
            0,
            0x004076B0,
            target_ip,
            0,
            NULL
        );

        if (hThread != 0) {
            InterlockedIncrement(&worker_count);
            CloseHandle(hThread);
        }

        Sleep(50);
    }

cleanup:
    _endthreadex(0);
}
```

The pseudocode is a behavioral reconstruction of the observed assembly; function and variable names are analytical labels.

## Research Report

`0x00407720` is the **IPv4 target dispatcher and worker scheduler** of the analyzed network component.

Its execution can be summarized as:

```text
Local network configuration
        │
        ▼
0x00409160
        │
        │ generate IPv4 collection
        ▼
192.168.124.1 ... 192.168.124.254
        │
        ▼
0x00407720
        │
        ├── verify collection exists
        ├── calculate element count
        ├── iterate through IPv4 values
        ├── throttle worker creation
        ├── create worker at 0x004076B0
        ├── pass IPv4 value as argument
        ├── atomically update worker counter
        └── delay 50 ms before next iteration
        │
        ▼
0x004076B0
        │
        ▼
processing of individual IPv4 target
```

The function itself doesnt establish the network connection or implement the subsequent SMB behavior. Its role is to transform the IPv4 collection produced by `0x00409160` into independently scheduled worker executions.

The dynamic analysis then uses `192.168.124.128` as a controlled target from the generated address space. The target was configured with SMB available over TCP port `445`, providing the controlled environment required to follow the subsequent worker execution into the SMB-related code path.

The next stage is therefore the analysis of [0x004076B0](0x004076B0.md).

The objective is to trace the lifecycle of the IPv4 value received as the function argument and determine how the worker uses it. In particular, the analysis should establish whether the address is used for network communication and identify the protocol, service, connection mechanism, and subsequent actions associated with each target.

Once `0x004076B0` and its relevant child functions have been analyzed, the complete relationship between:

```text

0x004076B0 → target processing
```

Can be reconstructed and the final interpretation of this propagation-related execution chain can be documented with substantially higher confidence.
