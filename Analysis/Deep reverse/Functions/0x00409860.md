### 0x00409860 - Stack Probing and Large Stack Allocation

`0x00409860` is a compiler/runtime helper used to safely allocate a large stack frame. It is called from `0x00406F50` with `EAX = 0x20E4`, which represents the requested stack allocation size (8,420 bytes).

```asm
00406F50  mov eax,20E4
00406F55  call 409860
```

Because the requested allocation exceeds one memory page (`0x1000` bytes), the helper probes the stack before changing `ESP`. On Windows x86, this mechanism prevents the function from jumping over the stack guard page when creating a large local frame.

#### 1. Check whether the allocation exceeds one page

```asm
00409861  cmp eax,1000
00409866  lea ecx,[esp+8]
0040986A  jb 409880
```

At function entry:

```text
EAX = 0x20E4
PAGE_SIZE = 0x1000
```

Since `0x20E4 > 0x1000`, execution continues into the page-probing loop.

`LEA ECX,[ESP+8]` establishes a stack address relative to the original stack pointer. The offset accounts for the stack state created by the call and the initial `push ecx`.

#### 2. Probe the stack page by page

```asm
0040986C  sub ecx,1000
00409872  sub eax,1000
00409877  test dword ptr [ecx],eax
```

The helper decreases `ECX` by one page (`0x1000`) and decreases `EAX` by the same amount.

The important instruction is:

```asm
test dword ptr [ecx],eax
```

The result of the `TEST` operation is not important for the algorithm. The memory operand `[ECX]` deliberately accesses the corresponding stack page.

This sequential memory access is the actual stack probe: it ensures that each page between the current stack position and the requested final stack position is touched before the stack pointer is moved. Windows uses guard pages to grow the committed stack when these pages are accessed.

For the current allocation:

```text
Requested size = 0x20E4

0x20E4 - 0x1000 = 0x10E4
0x10E4 - 0x1000 = 0x0E4
```

Therefore, two complete 4-KB pages are probed, followed by a final partial adjustment of `0xE4` bytes.

#### 3. Continue while a full page remains

```asm
00409879  cmp eax,1000
0040987E  jae 40986C
```

If at least another `0x1000` bytes remain, execution returns to `0x0040986C` and probes the next page.

For this execution:

```text
EAX = 0x10E4  → probe another page
EAX = 0x0E4   → less than one page, leave the loop
```

#### 4. Calculate the final stack position

```asm
00409880  sub ecx,eax
```

After the complete pages have been processed, the remaining `0xE4` bytes are subtracted from `ECX`.

`ECX` now represents the final stack position required for the caller's large local frame.

#### 5. Preserve the original stack pointer

```asm
00409882  mov eax,esp
```

The original `ESP` is saved in `EAX`.

This is required because the helper will change `ESP`, but it still needs access to the caller's saved return address.

#### 6. Probe the final stack location

```asm
00409884  test dword ptr [ecx],eax
```

The final memory location is touched before the stack pointer is changed.

Again, the purpose of the instruction is primarily the memory access through `[ECX]`, not the logical `TEST` result.

#### 7. Move the stack pointer

```asm
00409886  mov esp,ecx
```

The stack is now moved to the calculated final position:

```text
ESP = new stack position
```

This is an important characteristic of the x86 stack-probing helper: unlike a simple probe routine, this helper also performs the actual stack-pointer adjustment.

#### 8. Recover the saved return address

```asm
00409888  mov ecx,dword ptr [eax]
0040988A  mov eax,dword ptr [eax+4]
```

`EAX` still contains the original `ESP`.

The helper retrieves the values that were located at the original stack position:

```text
[old ESP]     → saved ECX
[old ESP + 4] → return address
```

The return address is therefore loaded into `EAX`.

#### 9. Return to the caller

```asm
0040988D  push eax
0040988E  ret
```

The recovered return address is pushed onto the newly adjusted stack and `RET` transfers execution back to the caller.

Execution therefore resumes at:

```text
0x00406F5A
```

in `0x00406F50`.

### Reconstructed flow

```text
0x00406F50
    │
    │ EAX = 0x20E4
    ▼
0x00409860
    │
    ├── compare allocation with 0x1000
    │
    ├── subtract 0x1000 from ECX/EAX
    │
    ├── touch [ECX]        ← stack page probe
    │
    ├── repeat while EAX >= 0x1000
    │
    ├── process remaining 0xE4 bytes
    │
    ├── touch final stack location
    │
    ├── ESP = calculated stack position
    │
    ├── recover return address
    │
    └── RET
         │
         ▼
0x00406F5A
```

### Relevance to the malware analysis

`0x00409860` doesnt perform network communication, payload transformation, encryption, or payload construction. It is a compiler/runtime support routine required because `0x00406F50` uses a large local stack frame.

The malware-specific logic begins again at `0x00406F5A`, where `0x00406F50` continues with register preservation and initialization of its large local buffers.

Therefore, `0x00409860` should be treated as **runtime infrastructure rather than part of the payload-transfer logic**.
