## 1. Overview

Function `0x00407F30` implements the service control handler previously registered by the service entry point at `0x00408000`.

During service initialization, the sample passes the address of this function to:

```c
RegisterServiceCtrlHandlerA(
    "mssecsvc2.0",
    0x00407F30
);
```

The Service Control Manager (SCM) subsequently invokes this callback when a control request is delivered to the service.

The function receives a single service control code and uses a compiler-generated jump table to dispatch the corresponding handler logic. The selected branch modifies the global `SERVICE_STATUS` structure at `0x00431430` and finally reports the resulting state to the SCM through `SetServiceStatus`.

The function therefore represents the **service control and status-reporting layer** of the sample rather than its primary network or propagation logic.

---

## 2. Function Input

The first instruction retrieves the function argument:

```asm
0x00407F30 | 8B4424 04 | mov eax,dword ptr ss:[esp+4]
```

On x86, the first stack argument is located at:

```text
[ESP + 4]
```

because the return address occupies `[ESP]`.

This value represents the Windows service **control code** supplied by the Service Control Manager.

The following instructions normalize the value:

```asm
0x00407F34 | 48       | dec eax
0x00407F35 | 83F8 04  | cmp eax,4
0x00407F38 | 77 3A    | ja 0x00407F74
```

The function subtracts `1` from the control code and checks whether the resulting value is greater than `4`.

This transformation allows the sample to use the control code as an index into a compact jump table.

---

## 3. Jump-Table Dispatch

The central dispatch mechanism is:

```asm
0x00407F3A | FF2485 8C7F4000 | jmp dword ptr ds:[eax*4+407F8C]
```

Conceptually, this corresponds to:

```c
switch (controlCode - 1)
{
    ...
}
```

The compiler implements the switch using an indirect jump table located at:

```text
0x00407F8C
```

Each table entry contains a 32-bit address of the corresponding branch.

The range check before the jump ensures that values outside the supported range are redirected to the common status-reporting path at `0x00407F74`.

This is a conventional compiler-generated implementation of a small `switch` statement.

---

## 4. Control-Code Branches

The available branches modify the `dwCurrentState` field of the global `SERVICE_STATUS` structure.

The structure was previously initialized by `0x00408000` at:

```text
0x00431430
```

with the following relevant layout:

```text
0x00431430  dwServiceType
0x00431434  dwCurrentState
0x00431438  dwControlsAccepted
0x0043143C  dwWin32ExitCode
0x00431440  dwServiceSpecificExitCode
0x00431444  dwCheckPoint
0x431448  dwWaitHint
```

### 4.1 STOPPED State

One branch executes:

```asm
0x00407F41 | 33C0                   | xor eax,eax
0x00407F43 | C705 34144300 01000000 | mov dword ptr ds:[431434],1
0x00407F4D | A3 3C144300            | mov dword ptr ds:[43143C],eax
0x00407F52 | A3 44144300            | mov dword ptr ds:[431444],eax
0x00407F57 | A3 48144300            | mov dword ptr ds:[431448],eax
```

The value written to:

```text
0x00431434 = 1
```

corresponds to:

```text
SERVICE_STOPPED
```

The function also clears:

```text
dwWin32ExitCode
dwCheckPoint
dwWaitHint
```

because `EAX` was first zeroed.

The resulting state can therefore be represented as:

```c
g_ServiceStatus.dwCurrentState = SERVICE_STOPPED;
g_ServiceStatus.dwWin32ExitCode = 0;
g_ServiceStatus.dwCheckPoint = 0;
g_ServiceStatus.dwWaitHint = 0;
```

The execution then continues to the common status-reporting block.

---

## 5. PAUSED State

Another branch performs:

```asm
0x00407F5E | C705 34144300 07000000 | mov dword ptr ds:[431434],7
```

The value:

```text
0x07
```

corresponds to:

```text
SERVICE_PAUSED
```

Thus:

```c
g_ServiceStatus.dwCurrentState = SERVICE_PAUSED;
```

No additional service-specific processing is performed in this branch before execution reaches the common reporting code.

---

## 6. RUNNING State

The third visible state transition is:

```asm
0x00407F6A | C705 34144300 04000000 | mov dword ptr ds:[431434],4
```

The value:

```text
0x04
```

corresponds to:

```text
SERVICE_RUNNING
```

Therefore:

```c
g_ServiceStatus.dwCurrentState = SERVICE_RUNNING;
```

Again, execution continues to the common reporting block.

It is important to distinguish this operation from the earlier transition performed by `0x00408000`: there, the service enters `SERVICE_RUNNING` during initial service startup. Here, the same status value is available as one of the states handled by the registered control callback.

---

## 7. Common Status-Reporting Path

All supported branches converge at:

```asm
0x00407F74 | 8B0D 5C144300 | mov ecx,dword ptr ds:[43145C]
0x00407F7A | 68 30144300   | push wannacry.431430
0x00407F7F | 51            | push ecx
0x00407F80 | FF15 0CA04000 | call dword ptr ds:[<SetServiceStatus>]
```

The first instruction retrieves the service status handle stored earlier by `0x00408000`:

```text
[0x0043145C]
```

This handle was returned by:

```c
RegisterServiceCtrlHandlerA(
    "mssecsvc2.0",
    0x00407F30
);
```

The function then passes two arguments to:

```c
SetServiceStatus(
    SERVICE_STATUS_HANDLE,
    &SERVICE_STATUS
);
```

Specifically:

```text
ECX = [0x0043145C]   → service status handle

push 0x00431430      → address of SERVICE_STATUS
push ECX           → service status handle
call SetServiceStatus
```

Because x86 Windows API calls use the stack for arguments, the resulting call is conceptually:

```c
SetServiceStatus(
    g_ServiceStatusHandle,
    &g_ServiceStatus
);
```

The return value from `SetServiceStatus` isnt subsequently evaluated by this function.

## 8. Reconstructed High-Level Logic

The observed assembly can be approximately represented as:

```c
void WINAPI ServiceCtrlHandler(DWORD controlCode)
{
    switch (controlCode)
    {
        case CONTROL_CODE_1:
            g_ServiceStatus.dwCurrentState = SERVICE_STOPPED;
            g_ServiceStatus.dwWin32ExitCode = 0;
            g_ServiceStatus.dwCheckPoint = 0;
            g_ServiceStatus.dwWaitHint = 0;
            break;

        case CONTROL_CODE_2:
            g_ServiceStatus.dwCurrentState = SERVICE_PAUSED;
            break;

        case CONTROL_CODE_3:
            g_ServiceStatus.dwCurrentState = SERVICE_RUNNING;
            break;

        default:
            break;
    }

    SetServiceStatus(
        g_ServiceStatusHandle,
        &g_ServiceStatus
    );
}
```

The exact symbolic mapping of every jump-table index to the original Windows control-code constants should be derived from the jump-table entries and the preceding `controlCode - 1` transformation rather than inferred solely from the resulting states.

This distinction is important because the function's **state values** (`SERVICE_STOPPED`, `SERVICE_PAUSED`, `SERVICE_RUNNING`) are directly established by the assembly, while the exact mapping between each incoming SCM control code and its branch requires examination of the jump table itself.

## 9. Relationship With `0x00408000`

The two functions form a direct service-management pair:

```text
0x00408000
   │
   ├── RegisterServiceCtrlHandlerA(
   │       "mssecsvc2.0",
   │       0x00407F30
   │   )
   │
   ├── initialize SERVICE_STATUS
   │
   ├── SetServiceStatus(SERVICE_RUNNING)
   │
   └── call 0x00407BD0
             │
             │
             ▼
       main service execution


SCM control request
        │
        ▼
   0x00407F30
        │
        ├── decode control code
        ├── update SERVICE_STATUS
        └── SetServiceStatus()
```

Therefore, `0x00408000` establishes the service and registers the callback, while `0x00407F30` provides the callback used for subsequent SCM control notifications.

This separation is consistent with the normal Windows service architecture.

## 10. Security-Relevant Interpretation

From a malware-analysis perspective, the important observation isnt that the implementation itself is unusual, but that the sample exposes a conventional Windows service-management interface.

The function demonstrates that:

1. `mssecsvc2.0` is registered as a Windows service.
    
2. The sample registers `0x00407F30` as its service control handler.
    
3. Incoming SCM control codes are dispatched through a jump table.
    
4. The handler modifies a global `SERVICE_STATUS` structure.
    
5. The resulting status is reported through `SetServiceStatus`.
    

No evidence in this function alone demonstrates an attempt to bypass or deceive the Service Control Manager.

Likewise, the presence of conventional service APIs shouldnt by itself be interpreted as an evasion technique. The relevant finding is that the sample implements the expected callback mechanism required for SCM-managed services.

The security significance comes primarily from the **role of this service within the larger WannaCry execution architecture**, rather than from any unusual property of the callback implementation itself.

## 13. Research Report

Function `0x00407F30` is the registered **Windows Service Control Handler** for the `mssecsvc2.0` service.

The function receives a control code from the Service Control Manager, dispatches it through a compiler-generated jump table, modifies the global `SERVICE_STATUS` structure, and reports the resulting state through `SetServiceStatus`.

The implementation is relatively small and conventional, but it is important for reconstructing the service architecture of the sample because it establishes the callback relationship between the Service Control Manager and the malware's service process.

Together with `0x00408000`, the function defines the service-management layer:

```text
0x00408000
    │
    ├── RegisterServiceCtrlHandlerA
    │        │
    │        └── 0x00407F30
    │
    ├── initialize SERVICE_STATUS
    ├── SetServiceStatus(SERVICE_RUNNING)
    └── 0x00407BD0
```

while `0x00407F30` handles subsequent service-control notifications:

```text
SCM
 │
 │ control code
 ▼
0x00407F30
 │
 ├── dispatch
 ├── update SERVICE_STATUS
 └── SetServiceStatus()
```

This completes the service-control portion of the reconstructed execution architecture and provides the transition point from Windows service management to the sample's main execution logic at `0x00407BD0`.
