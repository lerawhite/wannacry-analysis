# Network Worker Initialization and Thread Dispatcher — `0x00407BD0`

## 1. Overview

Function `0x00407BD0` represents an important execution boundary in the service-side network component of the sample.

Its first operation is a call to:

```asm
00407BD0 | E8 BBFFFFFF | call wannacry.407B90
```

The return value of [0x00407B90](0x00407B90.md) is immediately tested:

```asm
00407BD5 | 85C0 | test eax,eax
00407BD7 | 75 01 | jne 407BDA
00407BD9 | C3    | ret
```

This establishes a critical dependency:

```text
0x00407BD0
     │
     ▼
0x00407B90
     │
     ├── EAX = 0 → terminate 0x00407BD0
     │
     └── EAX ≠ 0 → continue
                  │
                  ▼
          worker initialization
```

Therefore, `0x00407B90` isnt simply another initialization routine called along the way. Its return value acts as a **gate condition for the entire subsequent execution path**.

If `0x00407B90` returns zero, `0x00407BD0` performs no thread creation and immediately returns to its caller.

If `0x00407B90` returns non-zero, execution proceeds into the worker initialization and dispatch logic.

This makes `0x00407B90` a **critical prerequisite for subsequent execution of the network worker subsystem**.

---

# 2. Critical Initialization Gate: `0x00407B90`

The function begins with:

```asm
00407BD0 | E8 BBFFFFFF | call wannacry.407B90
00407BD5 | 85C0        | test eax,eax
00407BD7 | 75 01      | jne 407BDA
00407BD9 | C3         | ret
```

The equivalent high-level logic is:

```c
if (!0x00407B90())
    return;
```

The exact internal reason why [0x00407B90](0x00407B90.md) can return zero **must be established from the analysis of that function itself.**

However, the caller's behavior is unambiguous: **the return value determines whether the remainder of `0x00407BD0` executes at all.**

This distinction is important for reconstructing the architecture.

The following operations:

- creation of the `0x00407720` thread;
    
- creation of the `0x00407840` worker threads;
    
- the 128-iteration dispatch loop;
    
- the two-second delay between worker creation;
    

are all **conditionally dependent on successful completion of `0x00407B90`**.

Therefore, the execution hierarchy should be represented as:

```text
0x00407BD0
    │
    ├── call 0x00407B90
    │
    ├── EAX == 0
    │      └── return
    │
    └── EAX != 0
           │
           ├── create 0x00407720 thread
           │
           └── create 0x00407840 workers
                    │
                    └── 128 iterations
```

---

# 3. Initial Worker Creation: `0x00407720`

After the initialization gate succeeds, the function saves registers and obtains the address of `_beginthreadex`:

```asm
00407BDE | 8B3D 1CA14000 | mov edi,dword ptr ds:[<_beginthreadex>]
```

The following arguments are pushed:

```asm
00407BE4 | 6A 00           | push 0
00407BE6 | 6A 00           | push 0
00407BE8 | 6A 00           | push 0
00407BEA | 68 20774000     | push wannacry.407720
00407BEF | 6A 00           | push 0
00407BF1 | 6A 00           | push 0
00407BF3 | FFD7            | call edi
```

For `_beginthreadex`, the relevant conceptual prototype is:

```c
uintptr_t _beginthreadex(
    void *security,
    unsigned stack_size,
    unsigned (__stdcall *start_address)(void *),
    void *arglist,
    unsigned initflag,
    unsigned *thrdaddr
);
```

The observed call therefore corresponds approximately to:

```c
_beginthreadex(
    NULL,
    0,
    0x00407720,
    NULL,
    0,
    NULL
);
```

The important characteristics are:

```text
Thread entry point:
    0x00407720

Thread argument:
    NULL

Creation flags:
    0

Stack size:
    default
```

Thus, `0x00407720` is launched once as an independent thread and receives no explicit argument from `0x00407BD0`.

The exact role of this thread is analyzed separately in the report for [0x00407720](0x00407720.md).

---

# 4. Thread Handle Management

Immediately after `_beginthreadex`, the return value is checked:

```asm
00407BF5 | 8B2D 78A04000 | mov ebp,dword ptr ds:[<CloseHandle>]
00407BFB | 83C4 18       | add esp,18
00407BFE | 85C0          | test eax,eax
00407C00 | 74 03         | je 407C05
00407C02 | 50            | push eax
00407C03 | FFD5          | call ebp
```

`_beginthreadex` returns a thread handle on success.

If the return value is non-zero, the handle is passed to:

```c
CloseHandle(threadHandle);
```

Therefore:

```c
HANDLE hThread = (HANDLE)_beginthreadex(...);

if (hThread != NULL)
    CloseHandle(hThread);
```

This is an important distinction.

`CloseHandle` doesnt terminate the newly created thread.

It closes the caller's handle to the thread object while the thread itself remains independently scheduled by Windows.

**Consequently, the main routine doesnt retain a thread handle for later synchronization or waiting.**

The same handle-management pattern is subsequently used for the worker threads.

---

# 5. Initialization of the Worker Counter

The function then loads the address of `Sleep`:

```asm
00407C05 | 8B1D A4A04000 | mov ebx,dword ptr ds:[<Sleep>]
```

and initializes:

```asm
00407C0B | 33F6 | xor esi,esi
```

Therefore:

```c
ESI = 0;
```

At this point, `ESI` becomes the loop counter and, importantly, is also passed as the argument to each `0x00407840` worker thread.

---

# 6. Worker Thread Creation

The main loop begins at:

```asm
00407C0D | 6A 00           | push 0
00407C0F | 6A 00           | push 0
00407C11 | 56              | push esi
00407C12 | 68 40784000     | push wannacry.407840
00407C17 | 6A 00           | push 0
00407C19 | 6A 00           | push 0
00407C1B | FFD7            | call edi
```

Conceptually:

```c
_beginthreadex(
    NULL,
    0,
    0x00407840,
    (void *)ESI,
    0,
    NULL
);
```

The critical difference from the previous thread creation is the fourth argument:

```text
arglist = ESI
```

Therefore, every [0x00407840](0x00407840.md) thread receives the current loop counter as its thread argument.

At the beginning of the loop:

```text
ESI = 0
```

so the first worker receives:

```text
argument = 0
```

After the iteration:

```asm
00407C2E | 46 | inc esi
```

so the next worker receives:

```text
argument = 1
```

and so on.

This creates a sequence of worker arguments:

```text
0, 1, 2, 3, ... , 127
```

The significance of this argument is determined by the implementation of `0x00407840` and should therefore be analyzed there rather than inferred solely from this dispatcher.

---

# 7. Worker Creation Failure Is Non-Fatal

As with the initial `0x00407720` thread, the return value of `_beginthreadex` is checked:

```asm
00407C1D | 83C4 18 | add esp,18
00407C20 | 85C0    | test eax,eax
00407C22 | 74 03   | je 407C27
00407C24 | 50      | push eax
00407C25 | FFD5    | call ebp
```

If `_beginthreadex` succeeds:

```text
EAX != 0
    │
    ▼
CloseHandle(EAX)
```

If `_beginthreadex` fails:

```text
EAX == 0
    │
    ▼
continue loop
```

**There is no retry, error propagation, or immediate termination.**

Thus, the successful creation of an individual `0x00407840` worker is **not a critical condition for continuation of the dispatcher**.

This is different from `0x00407B90`.

The architecture therefore contains two different levels of dependency:

```text
0x00407B90
    │
    └── critical gate
         │
         ├── failure → entire dispatcher terminates
         │
         └── success → worker creation begins


Individual _beginthreadex(0x00407840)
    │
    ├── success → handle closed, continue
    │
    └── failure → continue loop anyway
```

This distinction is important when reconstructing the reliability characteristics of the worker subsystem.

---

# 8. Two-Second Inter-Worker Delay

After each worker creation attempt, the function executes:

```asm
00407C27 | 68 D0070000 | push 7D0
00407C2C | FFD3        | call ebx
```

`0x7D0` hexadecimal equals:

```text
0x7D0 = 2000 ms
```

Therefore:

```c
Sleep(2000);
```

The delay occurs **after each worker creation attempt and before the loop proceeds to the next iteration**.

The relevant sequence is:

```text
create worker
     │
     ▼
CloseHandle (if creation succeeded)
     │
     ▼
Sleep(2000 ms)
     │
     ▼
ESI++
     │
     ▼
create next worker
```

Thus, the function doesnt create all 128 workers immediately.

Instead, worker creation is temporally staggered.

---

# 9. Worker Count

The loop termination condition is:

```asm
00407C2E | 46           | inc esi
00407C2F | 81FE 80000000| cmp esi,80
00407C35 | 7C D6        | jl 407C0D
```

The loop continues while:

```text
ESI < 0x80
```

Since:

```text
0x80 = 128
```

and `ESI` begins at zero, the worker creation loop executes for:

```text
ESI = 0 ... 127
```

Therefore, `0x00407840` is invoked through `_beginthreadex` **128 times**.

The argument supplied to those workers follows the same range:

```text
0 → 127
```

This gives the following conceptual structure:

```c
for (int i = 0; i < 128; i++)
{
    HANDLE h = (HANDLE)_beginthreadex(
        NULL,
        0,
        0x00407840,
        (void *)i,
        0,
        NULL
    );

    if (h != NULL)
        CloseHandle(h);

    Sleep(2000);
}
```

This is a reconstruction of the observed control flow; the exact original source code isnt known.

# 10. Staggered Worker-Launch Architecture

The combined behavior of the loop can be represented as:

```text
ESI = 0
   │
   ▼
Create 0x00407840(arg=0)
   │
   ▼
Sleep(2000)
   │
   ▼
ESI = 1
   │
   ▼
Create 0x00407840(arg=1)
   │
   ▼
Sleep(2000)
   │
   ▼
...
   │
   ▼
Create 0x00407840(arg=127)
   │
   ▼
Sleep(2000)
   │
   ▼
ESI = 128
   │
   ▼
loop terminates
```

This can be described as a **staggered worker-launch mechanism**.

The important experimentally supported observation is the timing relationship:

> A new worker-launch attempt occurs once every approximately two seconds, subject to the execution time of the preceding operations.

It is better not to characterize the delay as definitively being a throttling or evasion mechanism. The function establishes the timing behavior, but the design motivation cannot be proven from `0x00407BD0` alone.

Possible interpretations include controlling the rate of worker creation or pacing network activity, but these remain hypotheses until correlated with the worker implementation and broader execution behavior.

# 11. Relationship Between `0x00407720` and `0x00407840`

The function creates two different categories of threads.

### Initialization thread

```text
Entry point:
    0x00407720

Created:
    once

Argument:
    NULL
```

### Worker threads

```text
Entry point:
    0x00407840

Created:
    128 times

Arguments:
    0 ... 127

Delay:
    2000 ms between creation attempts
```

This strongly suggests a division of responsibilities:

```text
0x00407BD0
      │
      ├───────────────┐
      │               │
      ▼               ▼
0x00407720       0x00407840
initialization       workers
      │               │
      │               └── argument 0..127
      │
      └── separate execution path
```

However, the exact role of each thread should be established from the corresponding functions rather than assumed from their creation pattern.

# 12. Architectural Significance of `0x00407B90`

The most important finding in this function is the position of `0x00407B90` at the beginning of the execution chain.

The sequence is:

```text
ServiceMain / 0x00408000
        │
        ▼
   0x00407BD0
        │
        ▼
   0x00407B90
        │
        ├── failure → return
        │
        └── success
              │
              ▼
       create 0x00407720
              │
              ▼
       create 0x00407840
              │
              ▼
        128 workers
```

This makes `0x00407B90` the **critical initialization gate** for the subsequent worker subsystem.

In practical terms, the function doesnt attempt to start the worker architecture before `0x00407B90` reports success.

The distinction between initialization failure and individual worker-creation failure is particularly important:

|Event|Result|
|---|---|
|`0x00407B90` returns `0`|`0x00407BD0` terminates immediately|
|`0x00407720` creation fails|Execution continues|
|Individual `0x00407840` creation fails|Loop continues|
|`0x00407840` creation succeeds|Handle is immediately closed|
|`ESI == 128`|Worker creation loop terminates|

Therefore, `0x00407B90` has a substantially different architectural role from the individual worker-launch operations.

# 14. Dynamic Analysis Interpretation

The behavior observed in `0x00407BD0` is consistent with a dispatcher responsible for establishing and launching a concurrent worker subsystem.

The function itself does **not** perform the network communication represented by the lower-level networking functions already analyzed.

Instead, its role is orchestration:

```text
initialize prerequisite
        │
        ▼
start auxiliary thread
        │
        ▼
launch worker threads
        │
        ├── worker 0
        ├── worker 1
        ├── worker 2
        ├── ...
        └── worker 127
```

The actual network operations must therefore be attributed to the functions executed by these worker threads rather than to `0x00407BD0` itself.

This distinction is useful when constructing the final architecture diagram: `0x00407BD0` should be represented as a **dispatcher/orchestration layer**, while the actual network behavior belongs to the downstream worker functions.

# 15. Approximate High-Level Reconstruction

The complete function can be represented approximately as:

```c
void ServiceWorkerDispatcher(void)
{
    if (!0x00407B90())
        return;

    HANDLE hThread;

    hThread = (HANDLE)_beginthreadex(
        NULL,
        0,
        0x00407720,
        NULL,
        0,
        NULL
    );

    if (hThread != NULL)
        CloseHandle(hThread);

    for (unsigned i = 0; i < 128; i++)
    {
        hThread = (HANDLE)_beginthreadex(
            NULL,
            0,
            0x00407840,
            (void *)i,
            0,
            NULL
        );

        if (hThread != NULL)
            CloseHandle(hThread);

        Sleep(2000);
    }
}
```

This should be treated as a **behavioral reconstruction**, not a claim about the malware's original source code.

# 17. Research Report

Function `0x00407BD0` acts as a **worker-subsystem dispatcher** within the service execution path.

Its most significant characteristic is the dependency on `0x00407B90`. The function begins by calling `0x00407B90` and immediately evaluates its return value. A zero result terminates the function before any worker threads are created. Consequently, `0x00407B90` represents a **critical initialization gate for all subsequent execution performed by `0x00407BD0`**.

When the prerequisite succeeds, the function:

1. launches [0x00407720](0x00407720.md) once as an auxiliary thread;
    
2. initializes a worker counter;
    
3. launches [0x00407840](0x00407840.md) up to 128 times;
    
4. passes a unique index (`0..127`) to each worker;
    
5. closes each returned thread handle without terminating the worker;
    
6. introduces a 2000 ms delay between worker-launch attempts;
    
7. terminates the dispatch loop after the counter reaches `0x80`.
    

The resulting architecture is therefore:

```text
                 0x00407BD0
                       │
                       ▼
                 0x00407B90
                       │
                ┌──────┴──────┐
                │             │
             EAX=0         EAX!=0
                │             │
                ▼             ▼
             return      0x00407720
                              │
                              │
                              ▼
                       0x00407840
                              │
                    ┌─────────┴─────────┐
                    │                   │
                 worker 0           worker 127
                    │                   │
                    └─────────┬─────────┘
                              │
                       network execution
```

The next functions that need to be correlated with this dispatcher are therefore `0x00407720` and `0x00407840`. Their implementations will establish what the initial auxiliary thread performs, what the worker index represents, and how the worker subsystem connects to the network functions reconstructed elsewhere in the analysis.
