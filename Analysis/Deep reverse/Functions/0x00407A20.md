# Embedded PE and Self-Image Buffer Construction — `0x00407A20`

## 1. Overview

Function `0x00407A20` prepares two global memory buffers containing embedded PE blobs and a copy of the current executable.

The function performs four main operations:

1. Allocates two `0x50D800`- byte buffers.
    
2. Copies two embedded PE blobs from `.data` into the corresponding buffers.
    
3. Opens the current executable and appends its complete file image to the first buffer, preceded by its file size.
    
4. Copies this `[file_size][self executable]` region from the first buffer to the second buffer.
    

The resulting memory layout is:

```text
Buffer 1
[ PE blob #1 ][ DWORD file_size ][ self executable ]

Buffer 2
[ PE blob #2 ][ DWORD file_size ][ self executable ]
```

The function returns `1` on success and `0` on failure.

---

## 2. Buffer Allocation

The function first allocates two equally sized global memory regions using `GlobalAlloc`:

![](0x00407A20%20View%20in%20x64dbg%201%20part.png)

---

```asm
00407A2C | push 0x50D800
00407A31 | push 0x40
00407A4B | call esi(GlobalAlloc)
```

The arguments correspond to:

```c
GlobalAlloc(0x40, 0x50D800);
```

The returned pointers are stored globally:

```text
0x0070F864 → Buffer 1
0x0070F868 → Buffer 2
```

Observed allocations:

```text
Buffer 1 = 0x0307E020
Buffer 2 = 0x03596020
```

If the first allocation fails, the function immediately returns `0`.

If the second allocation fails, the first allocation is released with `GlobalFree`, followed by return `0`.

At this point:

```text
Buffer 1
┌─────────────────────────────────────────────────────────────┐
│                 0x50D800 bytes allocated                    │
└─────────────────────────────────────────────────────────────┘
0x0307E020
```

```text

│                 0x50D800 bytes allocated                    │
└─────────────────────────────────────────────────────────────┘
0x03596020
```

## 3. Embedded PE Selection and Copy

**Figure 2. `0x00407A20`View in x64dbg 2 part**
![](0x00407A20%20View%20in%20x64dbg%202%20part.png)

---


The function then iterates twice using `EDX` as an iterator:

```c
for (edx = 0; edx < 2; edx++)
```

The embedded PE source is selected based on the iteration:

```asm
00407A88 | mov esi, 0x0040B020
00407A8D | je  0x00407A94
00407A8F | mov esi, 0x0040F080
```

Therefore:

```text
Iteration 0 → PE blob #1 at 0x0040B020
Iteration 1 → PE blob #2 at 0x0040F080
```

The destination is selected from the global buffer pointers:

```asm
mov edi, [0x0070F864 + edx*4]
```

resulting in:

```text
Iteration 0 → Buffer 1 = 0x0307E020
Iteration 1 → Buffer 2 = 0x03596020
```

### Size selection

The function uses the same `neg → sbb → and` branchless selection pattern observed earlier:

```asm
mov eax, edx
neg eax
sbb eax, eax
and eax, 0x8844
add eax, 0x4060
```

This produces:

```text
Iteration 0:
    size = 0x4060

Iteration 1:
    size = 0x8844 + 0x4060
         = 0xC8A4
```

Thus the two embedded PE blobs have different sizes:

```text
PE blob #1 = 0x4060 bytes
PE blob #2 = 0xC8A4 bytes
```

The copy itself is performed using:

```asm
rep movsd
rep movsb
```

`rep movsd` copies the size divided by four, while `rep movsb` copies the remaining bytes.

After each iteration, the function calculates the end of the copied blob:

```text
buf_end = buf_begin + blob_size
```

---
*0x0307E020 + 0x4060 = **0x03082080** - first pe blob location borders.*

At this point, the two buffers contain only their respective embedded PE blobs.

## 4. Opening the Current Executable

The function then opens the current executable using `CreateFileA`:

```c
CreateFileA(
    "C:\\m_lab\\samples\\wannacry\\wannacry\\wannacry.exe",
    GENERIC_READ,
    FILE_SHARE_READ,
    NULL,
    OPEN_EXISTING,
    FILE_ATTRIBUTE_NORMAL,
    NULL
);
```

The observed handle is:

```text
hFile = 0x458
```

If `CreateFileA` returns `INVALID_HANDLE_VALUE`, both allocated buffers are released with `GlobalFree` and the function returns `0`.

## 5. Determining the Executable Size

The file size is obtained with:

```asm
00407B11 | push 0
00407B13 | push ebx
00407B14 | call GetFileSize
```

The observed result is:

```text
file_size = 0x0038D01D
```

The current end of Buffer 1 is:

```text
buf1_end = 0x03082080
```

Before reading the file, the function stores the file size directly at this address:

```asm
mov [buf1_end], file_size
```

Therefore:

```text
0x03082080 = 0x0038D01D
```

The actual executable data is then read starting four bytes later:

```asm
lea ecx, [esi+4]
```

giving:

```text
read destination = 0x03082084
```

This creates the following structure:

```text
Buffer 1

0x03082080
      │
      ▼
┌───────────────┬───────────────────────────────┐
│ DWORD         │                               │
│ file_size     │ self executable               │
│ 0x0038D01D    │ 0x0038D01D bytes              │
└───────────────┴───────────────────────────────┘
^               ^
buf1_end        buf1_end + 4
```

The `ReadFile` call therefore reads the complete executable directly into the space immediately following the stored size.

## 6. Reading the Self Executable

**Figure 3. `0x00407A20`View in x64dbg 3 part**
![](0x00407A20%20View%20in%20x64dbg%203%20part.png)

---


The relevant call is effectively:

```c
DWORD bytesRead;

ReadFile(
    hFile,
    (LPVOID)(buf1_end + 4),
    file_size,
    &bytesRead,
    NULL
);
```

The function then compares:

```text
bytesRead == file_size
```

In the observed execution:

```text
bytesRead = 0x0038D01D
file_size = 0x0038D01D
```

Therefore the read is considered successful.

If the number of bytes read doesnt match the expected file size, the function closes the file, frees both buffers and returns `0`.

## 7. Final Buffer 1 Layout

After the successful `ReadFile`, Buffer 1 contains:

```text
Buffer 1
0x0307E020
    │
    ▼
┌──────────────────┬────────────────┬──────────────────────────┐
│ PE blob #1       │ DWORD          │ self executable           │
│ 0x4060 bytes     │ file_size      │ 0x0038D01D bytes          │
│                  │ 0x0038D01D     │                           │
└──────────────────┴────────────────┴──────────────────────────┘
                   ^
                   0x03082080
                   buf1_end
```

The complete occupied region is therefore:

```text
0x4060 + 4 + 0x0038D01D bytes
```

The important point is that the executable isnt stored in a separate temporary allocation. It is appended directly to the first buffer.

## 8. Copying the Self-Image to Buffer 2

After the complete executable has been placed in Buffer 1, the function prepares the same structure in Buffer 2.

It calculates:

```asm
lea ecx, [edi+4]
```

where `EDI = file_size`.

Therefore:

```text
copy_size = file_size + 4
           = 0x0038D021
```

The source is:

```text
Buffer 1 + PE blob #1 size
= 0x03082080
```

The destination is:

```text
Buffer 2 end
= 0x035A28C4
```

The function then performs:

```asm
rep movsd
rep movsb
```

to copy the entire:

```text
[ DWORD file_size ][ self executable ]
```

region.

Importantly, the embedded PE blob itself is **not** copied during this operation.

The resulting state is:

```text
Buffer 1

[ PE blob #1 ][ DWORD file_size ][ self executable ]
                     │
                     └──────────────┐
                                    │
                                    ▼
Buffer 2

[ PE blob #2 ][ DWORD file_size ][ self executable ]
```

More precisely:

```text
Buffer 1
┌──────────────┬───────────────────────────────────────────────┐
│ PE blob #1   │ DWORD file_size │ self executable             │
│ 0x4060       │ +4 bytes        │ 0x0038D01D bytes            │
└──────────────┴───────────────────────────────────────────────┘
               │
               │ copy 0x0038D021 bytes
               ▼
Buffer 2
┌──────────────┬───────────────────────────────────────────────┐
│ PE blob #2   │ DWORD file_size │ self executable             │
│ 0xC8A4       │ +4 bytes        │ 0x0038D01D bytes            │
└──────────────┴───────────────────────────────────────────────┘
```

*0x035a28c4 + 0x38d01d = **0x0392F8E5**  - second extracted exe boundaries.*

After the copy completes, the file handle is closed:

```asm
CloseHandle(hFile);
```

The function then returns:

```asm

```

indicating successful completion.

All failure paths observed in the function return:

```text
EAX = 0
```

and release the allocated buffers before returning.

## 10. Reconstructed Logic

The overall behaviour can be represented as:

```c
BOOL PrepareBuffers(void)
{
    Buffer1 = GlobalAlloc(0x40, 0x50D800);
    if (!Buffer1)
        return FALSE;

    Buffer2 = GlobalAlloc(0x40, 0x50D800);
    if (!Buffer2) {
        GlobalFree(Buffer1);
        return FALSE;
    }

    copy(PE_blob_1, Buffer1, 0x4060);
    copy(PE_blob_2, Buffer2, 0xC8A4);

    HANDLE hFile = CreateFileA(
        "...\\wannacry.exe",
        GENERIC_READ,
        FILE_SHARE_READ,
        NULL,
        OPEN_EXISTING,
        FILE_ATTRIBUTE_NORMAL,
        NULL
    );

    if (hFile == INVALID_HANDLE_VALUE) {
        GlobalFree(Buffer1);
        GlobalFree(Buffer2);
        return FALSE;
    }

    DWORD fileSize = GetFileSize(hFile, NULL);

    *(DWORD *)(Buffer1 + 0x4060) = fileSize;

    DWORD bytesRead;
    ReadFile(
        hFile,
        Buffer1 + 0x4060 + 4,
        fileSize,
        &bytesRead,
        NULL
    );

    if (bytesRead != fileSize) {
        CloseHandle(hFile);
        GlobalFree(Buffer1);
        GlobalFree(Buffer2);
        return FALSE;
    }

    memcpy(
        Buffer2 + 0xC8A4,
        Buffer1 + 0x4060,
        fileSize + 4
    );

    CloseHandle(hFile);

    return TRUE;
}
```

The pseudocode above represents the observed data flow; names such as `Buffer1`, `Buffer2`, and `PE_blob_1` are analytical labels rather than original symbols.

## Research Report

`0x00407A20` constructs two compound memory regions from embedded PE data and the current executable.

The final in-memory layout is:

```text
Buffer 1
[ PE blob #1 ][ file_size ][ self executable ]


Buffer 2
[ PE blob #2 ][ file_size ][ self executable ]
```

The first buffer is constructed directly from the embedded PE blob and the on-disk executable. The second buffer receives an exact copy of the `[file_size][self executable]` portion from the first buffer.

The function therefore establishes two independently allocated memory regions with different embedded PE prefixes but an identical appended copy of the current executable.
