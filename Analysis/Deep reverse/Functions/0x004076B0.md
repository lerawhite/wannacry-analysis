# Function `0x004076B0` - Per-Target Worker Dispatcher

## Overview

`0x004076B0` is a per-target worker routine invoked by the dispatcher at `0x00407720`. The function receives a single argument representing an IPv4 address generated by the preceding target-generation stage.

As a reminder, we chose `192.168.124.128` as the IP-address to be passed.

Its primary responsibility is to determine whether the supplied IP address should proceed to the next stage of network-related processing and, if so, create a secondary worker thread at `0x00407540`.

The execution flow can be summarized as:

```text
00407720
    │
    │ _beginthreadex(..., 004076B0, IPv4)
    ▼
004076B0
    │
    ├── 00407480(IPv4)
    │       │
    │       ├── return <= 0 → abort target
    │       │
    │       └── return > 0  → continue
    │
    ├── _beginthreadex(..., 00407540, IPv4)
    │
    ├── WaitForSingleObject(thread, 10 minutes)
    │
    ├── timeout → TerminateThread()
    │
    ├── CloseHandle()
    ├── InterlockedDecrement(0x0070F86C)
    └── _endthreadex()
```

Therefore, `0x004076B0` should be considered an **intermediate worker/dispatcher layer**, rather than the final network-processing routine itself.

---

## 1. Function Argument

At entry:

```asm
004076B0 | 56              | push esi
004076B1 | 8B7424 08       | mov esi,dword ptr ss:[esp+8]
```

The function retrieves its first argument from the stack and stores it in `ESI`.

This argument originates from the IPv4 target array constructed by `0x00409160` and distributed by `0x00407720`.

Conceptually:

```c
uint32_t target_ip = arg1;
```

The same value is subsequently passed to both `0x00407480` and, if that function succeeds, the secondary worker `0x00407540`.

---

# 2. Critical Gate: Function `0x00407480`

The first meaningful operation is:

```asm
004076B5 | 56              | push esi
004076B6 | E8 C5FDFFFF     | call 00407480
004076BB | 83C4 04         | add esp,4
004076BE | 85C0            | test eax,eax
004076C0 | 7E 40           | jle 00407702
```

The supplied IPv4 address is passed directly to [0x00407480](0x00407480.md).

The return value in `EAX` determines whether execution proceeds to the next stage:

```c
if (check_target(target_ip) <= 0)
    goto cleanup;
```

This makes `0x00407480` a **critical execution gate**.

---

### Control-flow consequence

If:

```text
00407480 → EAX <= 0
```

then execution immediately bypasses the `_beginthreadex` call for [0x00407540](0x00407540.md) .

Therefore:

```text
IPv4 target
     │
     ▼
00407480
     │
     ├── EAX <= 0 ─────→ no 00407540
     │
     └── EAX > 0
              │
              ▼
         create 00407540
```

At this stage, the exact semantics of `0x00407480` must therefore be established before the behavior of `0x00407540` can be fully understood.

**Consequently, `0x00407480` is a high-priority function for further reverse engineering.**

Understanding it will explain **why a particular generated IPv4 address is allowed to proceed into the next stage of WannaCry's network-processing chain.**

---

# 3. Creation of the Secondary Worker

If `0x00407480` returns a positive value, the function prepares a call to `_beginthreadex`:

```asm
004076C2 | 6A 00
004076C4 | 6A 00
004076C6 | 56              | push esi
004076C7 | 68 40754000     | push 00407540
004076CC | 6A 00
004076CE | 6A 00
004076D0 | FF15 ...         | call _beginthreadex
```

The important parameters are:

```text
start routine = 0x00407540
argument      = target IPv4 address
```

Thus `0x004076B0` doesnt itself perform the final target operation. Instead, it creates another execution context dedicated to [0x00407540](0x00407540.md).

The same IPv4 value received by `0x004076B0` is forwarded unchanged to the new worker.

Conceptually:

```c
HANDLE hThread = (HANDLE)_beginthreadex(
    NULL,
    0,
    worker_00407540,
    (void *)target_ip,
    0,
    NULL
);
```

---

# 4. Worker Creation Failure

The return value of `_beginthreadex` is stored in `ESI`:

```asm
004076D6 | 8BF0
004076D8 | 83C4 18
004076DB | 85F6
004076DD | 74 23
```

If the returned thread handle is zero, execution bypasses the waiting stage and proceeds directly to cleanup.

Therefore, the routine handles both cases:

```text
_beginthreadex
     │
     ├── failure → cleanup
     │
     └── success → wait for worker
```

---

# 5. Synchronous Waiting for the Secondary Worker

After successfully creating `0x00407540`, the function executes:

```asm
004076DF | 68 C0270900     | push 927C0
004076E4 | 56              | push esi
004076E5 | FF15 ...        | call WaitForSingleObject
```

`0x927C0` milliseconds corresponds to:

```text
600,000 ms
= 600 seconds
= 10 minutes
```

Therefore, `0x004076B0` waits up to **10 minutes** for the newly created `0x00407540` worker to terminate.

This is an important architectural detail: although the secondary operation executes in a separate thread, `0x004076B0` synchronizes with that thread before completing its own execution.

---

# 6. Timeout Handling

The return value from `WaitForSingleObject` is compared against:

```asm
004076EB | 3D 02010000     | cmp eax,102
004076F0 | 75 09           | jne 004076FB
```

`0x102` corresponds to `WAIT_TIMEOUT`.


 If `WaitForSingleObject` returns `WAIT_TIMEOUT`, the worker is forcibly terminated with `TerminateThread`.

```asm
004076F2 | 6A 00
004076F4 | 56
004076F5 | FF15 ...        | call TerminateThread
```


Conceptually:

```c
DWORD result = WaitForSingleObject(hThread, 600000);

if (result == WAIT_TIMEOUT)
    TerminateThread(hThread, 0);
```

This establishes an explicit execution-time limit for the secondary worker.

---

# 7. Handle Cleanup and Global Worker Counter

After the worker terminates normally or is forcibly terminated, the thread handle is closed:

```asm
004076FB | 56
004076FC | FF15 ...        | call CloseHandle
```

The global worker counter is then decremented:

```asm
00407702 | 68 6CF87000     | push 0070F86C
00407707 | FF15 ...        | call InterlockedDecrement
```

This corresponds to the worker-count mechanism previously observed in `0x00407720`.

The relationship is therefore:

```text
00407720
    │
    ├── InterlockedIncrement(0070F86C)
    │
    ▼
004076B0
    │
    ├── create secondary worker
    │
    └── InterlockedDecrement(0070F86C)
```

The use of `InterlockedDecrement` confirms that the counter is shared between threads and modified atomically.

This provides the synchronization mechanism used by the higher-level dispatcher to regulate worker creation.

---

# 8. Thread Termination

Finally:

```asm
0040770D | 6A 00
0040770F | FF15 ...        | call _endthreadex
00407715 | 83C4 04
00407718 | 33C0            | xor eax,eax
0040771A | 5E
0040771B | C3              | ret
```


The routine terminates the current CRT-managed thread with `_endthreadex(0)`. The instructions following the call form the compiler-generated epilogue and arent expected to execute during normal thread termination.

---

# 9. Reconstructed Control Flow

The current understanding can be represented as:

```c
void __cdecl WorkerDispatcher(uint32_t target_ip)
{
    if (CheckTarget_00407480(target_ip) <= 0)
        goto cleanup;

    HANDLE hThread = (HANDLE)_beginthreadex(
        NULL,
        0,
        Worker_00407540,
        (void *)target_ip,
        0,
        NULL
    );

    if (hThread != NULL)
    {
        DWORD result = WaitForSingleObject(
            hThread,
            600000        // 10 minutes
        );

        if (result == WAIT_TIMEOUT)
            TerminateThread(hThread, 0);

        CloseHandle(hThread);
    }

cleanup:
    InterlockedDecrement(&DAT_0070F86C);
    _endthreadex(0);
}
```

The pseudocode intentionally leaves [0x00407480](0x00407480.md) unresolved because its return value represents a critical decision point whose semantics must be established independently.

---

# 10. Current Architectural Interpretation

`0x004076B0` represents an additional layer in WannaCry's multithreaded network-processing architecture.

The previously analyzed dispatcher `0x00407720` distributes generated IPv4 targets among instances of `0x004076B0`.

Each instance then performs:

```text
target IP
   │
   ▼
00407480
   │
   │ target accepted?
   ├─────────────── No ─────→ terminate worker
   │
   Yes
   │
   ▼
_beginthreadex
   │
   ▼
00407540
   │
   └── target-specific processing
           │
           ▼
       completion
```

This reveals a **two-level worker architecture**:

```text
00407720
    │
    ├── 004076B0(IP #1)
    │       └── 00407540(IP #1)
    │
    ├── 004076B0(IP #2)
    │       └── 00407540(IP #2)
    │
    ├── 004076B0(IP #3)
    │       └── 00407540(IP #3)
    │
    └── ...
```



---
## Research report

Therefore, `0x004076B0` shouldt be interpreted as the final network worker. It functions as a **per-target gatekeeper and secondary-thread supervisor**.

The most important unresolved component is now `0x00407480`.

Its return value controls whether a generated target reaches [0x00407540](0x00407540.md), making it the next critical function to reverse engineer.
