## 1. Dynamic API Resolution

The function initially obtains a handle to `kernel32.dll`:

```
push    L"kernel32.dll"
call    GetModuleHandleW
mov     esi, eax
```

The returned module handle is then used with `GetProcAddress` to dynamically resolve several APIs:

```
CreateProcessA
CreateFileA
WriteFile
CloseHandle
```

The resolved addresses are stored in global variables:

```
431478 → CreateProcessA
431458 → CreateFileA
431460 → WriteFile
43144C → CloseHandle
```

Conceptually:

```
HMODULE hKernel32 = GetModuleHandleW(L"kernel32.dll");

CreateProcessA_ptr = GetProcAddress(hKernel32, "CreateProcessA");
CreateFileA_ptr    = GetProcAddress(hKernel32, "CreateFileA");
WriteFile_ptr     = GetProcAddress(hKernel32, "WriteFile");
CloseHandle_ptr   = GetProcAddress(hKernel32, "CloseHandle");
```

Each resolved address is checked against `NULL`. If any required API cant be resolved, execution follows the failure path at `0x00407F08`.

### Reverse-engineering significance

This is an example of **runtime API resolution** rather than relying exclusively on direct calls through the import table.

The function therefore establishes the required execution primitives dynamically before processing the embedded resource.

`IOC - Dynamic API resolve.`

This behavior should be correlated with the previously identified `GetModuleHandleA/W` and `GetProcAddress` imports from the static analysis.

# 2. Resource Identification and Extraction

After resolving the required APIs, the function accesses a resource embedded in the current PE image.

```
push    "R"
push    0x727
push    NULL
call    FindResourceA
```

The arguments correspond to:

```
FindResourceA(
    NULL,       // current module
    0x727,      // resource identifier
    "R"         // resource type
);
```

The `NULL` module handle indicates that the resource is searched for in the **current executable image.**

---

**Figure 2. `0x00407CE0` Rsrc**
![](../Screens/0x00407CE0%20Rsrc%20dump.png)


The returned resource handle is then processed through the standard Windows resource-access sequence:

```
FindResourceA
      ↓
LoadResource
      ↓
LockResource
      ↓
SizeofResource
```

Conceptually:

```
HRSRC hResource = FindResourceA(
    NULL,
    MAKEINTRESOURCEA(0x727),
    "R"
);

HGLOBAL hLoaded = LoadResource(NULL, hResource);

void *resourceData = LockResource(hLoaded);

DWORD resourceSize = SizeofResource(NULL, hResource);
```

The result of `LockResource` is stored at `[esp+10]`, while the resource size is stored in `EBP`.

The function checks **every stage for failure** and terminates through the common exit path if resource acquisition **is unsuccessful**.

---
### Significance

This is an important correlation with the earlier `.rsrc` analysis.

The static analysis established that the sample contains a **large embedded** resource structure containing an embedded PE/archive. This function demonstrates that the sample actively accesses resource data and obtains both:

- a pointer to the resource contents;
- the exact size of the resource.

The resource therefore represents **executable data that is subsequently processed by the function**, rather than merely unused application resources.

`IOC - Resource extraction / Resource ID 0x727.`

### 5.File Creation

**Figure 6. `0x00407CE0` CreateFileA arguments** 
![](../Screens/0x00407CE0%20CreateFileA%20arguments.png)


After constructing the target path `C:\WINDOWS\tasksche.exe`, the sample invokes `CreateFileA` through the previously resolved API address.

The arguments observed on the stack are:

```
lpFileName            = "C:\\WINDOWS\\tasksche.exe"
dwDesiredAccess       = 0x40000000  (GENERIC_WRITE)
dwShareMode           = 0
lpSecurityAttributes  = NULL
dwCreationDisposition = 0x00000002  (CREATE_ALWAYS)
dwFlagsAndAttributes  = 0x00000004  (FILE_ATTRIBUTE_SYSTEM)
hTemplateFile         = NULL
```

The call can therefore be represented as:

```
HANDLE hFile = CreateFileA(
    "C:\\WINDOWS\\tasksche.exe",
    GENERIC_WRITE,
    0,
    NULL,
    CREATE_ALWAYS,
    FILE_ATTRIBUTE_SYSTEM,
    NULL
);
```

`CREATE_ALWAYS` instructs Windows to create the file if it doesnt exist, or overwrite it if an existing file is found. The `FILE_ATTRIBUTE_SYSTEM` flag causes the resulting file to receive the **System** attribute.

During dynamic analysis, the call returned:

```
EAX = 0x00000440
```

which represents a valid file handle. The file `C:\WINDOWS\tasksche.exe` was subsequently observed on disk with an initial size of **0 bytes**. This confirms that this stage is responsible for creating the destination file, while the payload contents havent yet been written.

The execution therefore proceeds from resource extraction toward payload deployment:

```
Embedded Resource
      ↓
Resource data in memory
      ↓
CreateFileA
      ↓
C:\WINDOWS\tasksche.exe
      ↓
WriteFile
      ↓
Payload written to disk
```

At this point, the created file itself is an important behavioral indicator. The combination of the hard-coded system path, executable filename, `CREATE_ALWAYS`, `GENERIC_WRITE`, and `FILE_ATTRIBUTE_SYSTEM` provides strong evidence of deliberate payload deployment. The subsequent `WriteFile` call is therefore the next critical step for determining whether the extracted resource is written directly into `tasksche.exe`.

### 6.`WriteFile` — Writing the Extracted PE

**Figure 8. `0x00407CE0` WriteFile arguments** 
![](../Screens/0x00407CE0%20WriteFile%20arguments.png)

After creating the destination file, the sample prepares a `WriteFile` call to copy the extracted PE data from memory into the newly created file.

The arguments observed immediately before the call are:

```asm
hFile                  = 0x00000440
lpBuffer               = 0x007100A4  → "MZ..."
nNumberOfBytesToWrite  = 0x0035A000
lpNumberOfBytesWritten = 0x0019FC00
lpOverlapped            = NULL
```

These values correspond to the following call:

```c
DWORD bytesWritten;

WriteFile(
    0x00000440,
    (LPCVOID)0x007100A4,
    0x0035A000,
    &bytesWritten,
    NULL
);
```

The `lpBuffer` points to memory beginning with the `MZ` signature, indicating that the buffer contains PE-formatted executable data. The requested write size is `0x35A000` bytes, corresponding to the extracted payload size.

The arguments are prepared by the following sequence:

```
push ebx    ; lpOverlapped = NULL
push edx    ; lpNumberOfBytesWritten
push ebp    ; nNumberOfBytesToWrite = 0x35A000
push eax    ; lpBuffer = 0x007100A4
push esi    ; hFile = 0x440
call WriteFile
```

Therefore, this operation represents the transition from **in-memory resource extraction to filesystem deployment**:

```
Embedded PE resource
        ↓
PE data extracted into memory
        ↓
0x007100A4 ("MZ...")
        ↓
WriteFile
        ↓
C:\WINDOWS\tasksche.exe
        ↓
0x35A000 bytes written
```

This is dynamically confirmed as a payload-writing operation: the previously created `tasksche.exe` is populated with the PE data contained in the extracted resource.

**IOC reference:** `C:\WINDOWS\tasksche.exe` — link to the corresponding IOC entry.

**Behavioral significance:** this API call provides direct evidence that the embedded PE is being materialized as a standalone executable on disk. Together with the preceding `FindResourceA → LoadResource → LockResource → SizeofResource → CreateFileA` sequence, it establishes a complete resource-extraction and payload-deployment chain.

### 7.Process Creation

**Figure 10. `0x00407CE0` CreateProcessA arguments**
![](../Screens/0x00407CE0%20CreateProcessA%20arguments.png)

Following the extraction and reconstruction of the embedded PE, the sample prepares a `CreateProcessA` call to execute the newly created `tasksche.exe` file.

The runtime stack confirms the following parameters:

```c
lpApplicationName   = NULL
lpCommandLine       = "C:\\WINDOWS\\tasksche.exe /i"
lpProcessAttributes = NULL
lpThreadAttributes  = NULL
bInheritHandles     = FALSE
dwCreationFlags     = 0x08000000  (CREATE_NO_WINDOW)
lpEnvironment       = NULL
lpCurrentDirectory  = NULL
lpStartupInfo       = 0x0019FC14
lpProcessInformation= 0x0019FC04
```

The use of `lpApplicationName = NULL` causes the executable to be specified through the command line. The command line explicitly identifies the previously created `tasksche.exe` and passes the `/i` argument.

The `CREATE_NO_WINDOW` creation flag (`0x08000000`) indicates that the new process is created without a console window.

The resulting execution flow can therefore be summarized as:

```text
Embedded PE resource
        ↓
Resource extraction
        ↓
CreateFileA("C:\\WINDOWS\\tasksche.exe", ...)
        ↓
WriteFile(PE data)
        ↓
tasksche.exe
        ↓
CreateProcessA(
    "C:\\WINDOWS\\tasksche.exe /i",
    CREATE_NO_WINDOW
)
        ↓
New process execution
```

This provides dynamic evidence that the extracted PE isnt merely written to disk, but is subsequently executed as a separate process with the `/i` command-line argument.

`IOC / Behavioral Indicators`:

- `C:\WINDOWS\tasksche.exe` — dropped executable path.
    
- `tasksche.exe /i` — observed command-line execution.
    
- `CREATE_NO_WINDOW` — process creation without a console window.
    
- The execution of the resource-extracted PE establishes a direct connection between the embedded resource and the subsequent process execution stage.

## Research Report

### Drop-and-Execute Path

The analyzed function implements a complete **resource extraction, file deployment, and process execution chain**. The execution flow begins with runtime API resolution and terminates with the creation of a new `tasksche.exe` process.

#### 1. Dynamic API Resolution

The function first obtains the module handle of `kernel32.dll` using `GetModuleHandleW` and dynamically resolves the addresses of several APIs through `GetProcAddress`:

```
GetModuleHandleW("kernel32.dll")
        ↓
GetProcAddress("CreateProcessA")
GetProcAddress("CreateFileA")
GetProcAddress("WriteFile")
GetProcAddress("CloseHandle")
```

The resolved addresses are stored in global variables and subsequently used through indirect calls.

This provides a runtime API-resolution mechanism rather than directly invoking the corresponding imported functions.

#### 2. Resource Extraction

The function then accesses a resource embedded within the sample:

```
FindResourceA(NULL, 0x727, "R")
        ↓
LoadResource()
        ↓
LockResource()
        ↓
SizeofResource()
```

`hModule = NULL` indicates that the resource is searched within the current executable image.

`LockResource` returns a pointer to the resource data, while `SizeofResource` determines its size. Dynamic analysis confirmed that the resulting memory region begins with the `MZ` signature, providing evidence that the resource contains an embedded PE image.

#### 3. File Path Construction

The function constructs the destination path:

```
C:\WINDOWS\tasksche.exe
```

It also constructs a second path:

```
C:\WINDOWS\qeriuwjhrf
```

The latter is used as the source path for a `MoveFileExA` operation.

The observed call was:

```
MoveFileExA(
    "C:\\WINDOWS\\tasksche.exe",
    "C:\\WINDOWS\\qeriuwjhrf",
    1
);
```

During dynamic analysis, the destination file didnt previously exist and the call returned `0`. Execution nevertheless continued, indicating that failure of this operation isnt treated as a fatal condition in this path.

#### 4. Creation of the Dropped File

The sample subsequently creates:

```
C:\WINDOWS\tasksche.exe
```

with the following `CreateFileA` parameters:

```
CreateFileA(
    "C:\\WINDOWS\\tasksche.exe",
    GENERIC_WRITE,
    0,
    NULL,
    CREATE_ALWAYS,
    FILE_ATTRIBUTE_SYSTEM,
    NULL
);
```

The resulting handle is used to write the extracted PE data to disk.

The use of `CREATE_ALWAYS` ensures that the file is created or overwritten, while `FILE_ATTRIBUTE_SYSTEM` marks the resulting file with the Windows **System** attribute.

#### 5. Writing the Embedded PE

The resource buffer is written directly to the newly created file through `WriteFile`.

Dynamic analysis confirmed that the buffer begins with the PE `MZ` signature and that the previously empty `tasksche.exe` file becomes populated with the extracted PE data.

Conceptually:

```
WriteFile(
    hFile,
    peBuffer,
    peSize,
    &bytesWritten,
    NULL
);
```

This establishes the direct relationship between the embedded resource and the dropped executable.

#### 6. Command-Line Construction

The function constructs the following command line:

```
C:\WINDOWS\tasksche.exe /i
```

The `/i` argument is therefore not inferred from static strings alone; its presence was confirmed in the runtime stack immediately before `CreateProcessA`.

#### 7. Process Creation

Finally, the function prepares `STARTUPINFOA` and `PROCESS_INFORMATION` structures and invokes `CreateProcessA`.

The observed runtime call is equivalent to:

```
CreateProcessA(
    NULL,
    "C:\\WINDOWS\\tasksche.exe /i",
    NULL,
    NULL,
    FALSE,
    CREATE_NO_WINDOW,
    NULL,
    NULL,
    &startupInfo,
    &processInfo
);
```

The `CreateProcessA` API creates a new process and its primary thread.

The runtime `STARTUPINFOA` structure was observed as:

```
STARTUPINFOA startupInfo = {
    .cb              = 0x44,
    .lpReserved      = NULL,
    .lpDesktop       = NULL,
    .lpTitle         = NULL,
    .dwX             = 0,
    .dwY             = 0,
    .dwXSize         = 0,
    .dwYSize         = 0,
    .dwXCountChars   = 0,
    .dwYCountChars   = 0,
    .dwFillAttribute = 0,
    .dwFlags         = 0x81,
    .wShowWindow     = 0,
    .cbReserved2     = 0,
    .lpReserved2     = NULL,
    .hStdInput       = NULL,
    .hStdOutput      = NULL,
    .hStdError       = NULL
};
```

`dwCreationFlags = 0x08000000` corresponds to `CREATE_NO_WINDOW`, while `bInheritHandles = FALSE` prevents handle inheritance.

### Consolidated Execution Flow

```
GetModuleHandleW("kernel32.dll")
        ↓
Dynamic API resolution
        ↓
FindResourceA
        ↓
LoadResource
        ↓
LockResource
        ↓
SizeofResource
        ↓
Embedded PE (MZ...)
        ↓
Construct "C:\WINDOWS\tasksche.exe"
        ↓
CreateFileA(CREATE_ALWAYS | FILE_ATTRIBUTE_SYSTEM)
        ↓
WriteFile(embedded PE)
        ↓
tasksche.exe
        ↓
Construct command line:
"C:\WINDOWS\tasksche.exe /i"
        ↓
CreateProcessA(CREATE_NO_WINDOW)
        ↓
New process execution
```

### Behavioral Assessment

This sequence provides strong runtime evidence of a **drop-and-execute mechanism**. The sample extracts an embedded PE from its resources, creates a system-attributed executable in `C:\WINDOWS`, writes the embedded PE to disk, constructs a command line containing `/i`, and executes the resulting file as a separate process.

The combined artifacts constitute both **behavioral evidence and IOC candidates**, including:

- `C:\WINDOWS\tasksche.exe`
- `tasksche.exe /i`
- `FILE_ATTRIBUTE_SYSTEM`
- `CREATE_ALWAYS`
- the embedded PE resource
- execution of the extracted PE through `CreateProcessA`

This path is therefore no longer treated as a static hypothesis: the critical stages of the resource extraction, file creation, PE writing, and process execution were directly confirmed through dynamic analysis.
