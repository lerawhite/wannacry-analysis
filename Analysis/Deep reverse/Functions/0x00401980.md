# Function 0x00401980  SMB1 Protocol Qualification

## 1. Overview

Function `0x00401980` performs a multi-stage SMB1 protocol interaction with a remote IPv4 host over TCP port `445`.

The function is reached from the per-target processing routine `0x407540` after a preliminary TCP/445 connectivity check performed by `0x407480`.

While `0x407480` determines whether a TCP connection to port `445` can be established, `0x401980` performs a substantially deeper stateful SMB1 protocol exchange.

The observed execution can be summarized as:

```text
Target IPv4 address
        │
        ▼
inet_addr()
        │
        ▼
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP)
        │
        ▼
connect(target:445)
        │
        ▼
SMB_COM_NEGOTIATE
        │
        ▼
recv #1
        │
        ▼
SMB_COM_SESSION_SETUP_ANDX
        │
        ▼
recv #2
        │
        ▼
STATUS_ACCESS_DENIED
        │
        ▼
Extract SMB UID = 0x0000
        │
        ▼
0x4017B0
        │
        ├── construct \\<target>\IPC$
        ├── insert UID bytes
        └── rebuild SMB request
        │
        ▼
SMB_COM_TREE_CONNECT_ANDX
        │
        ▼
send #3
        │
        ▼
recv #3
        │
        └── WSAECONNRESET
```

A subsequent SMB `SMB_COM_TRANSACTION` request is present statically at `0x42E4F4`, containing a `\PIPE\` path, but this stage wasnt reached during the observed execution.

The important finding is that the third request depends on information returned by the Session Setup response. In the observed execution, the target returned `STATUS_ACCESS_DENIED` and a UID value of `0x0000`. This UID was then incorporated into the third SMB request by `0x4017B0`.

Because no valid SMB user/session context was established in the observed exchange, the subsequent Tree Connect stage didnt produce a valid response and the TCP connection was reset by the peer. Analysis of this execution therefore terminates at this stage.

# 3. TCP Socket Establishment

The function creates a conventional IPv4 TCP socket:

```asm
push 0
push 1
push 2
call socket
```

corresponding to:


The return value is checked against `INVALID_SOCKET` (`0xFFFFFFFF`).

If socket creation fails, execution branches to the failure path and eventually returns `0`.

If successful, the socket handle is preserved in `ESI` and subsequently reused for all SMB exchanges.

The function then calls:

```c
connect(socket, sockaddr, 0x10);
```

The result is checked against `SOCKET_ERROR`.

In the observed execution:

```text

connect() → 0
```

Therefore, the TCP connection to:

```text
192.168.124.128:445
```

was successfully established.

# 8. Critical Finding - Session Setup Returned STATUS_ACCESS_DENIED

The SMB status field in the response is:

```text
22 00 00 C0
```

SMB status fields are little-endian, therefore:

```text
0xC0000022
```

which corresponds to:

```text
STATUS_ACCESS_DENIED
```

This is a critical point in the execution.

The first SMB negotiation succeeded:

```text
SMB_COM_NEGOTIATE
        ↓
STATUS_SUCCESS
```

but the subsequent Session Setup request was rejected:

```text
SMB_COM_SESSION_SETUP_ANDX
        ↓
STATUS_ACCESS_DENIED
```

Therefore, the observed execution did **not** establish a successful authenticated SMB user/session context.

The response should consequently not be interpreted as a successful login or as successful SMB authentication.

The sequence is:

```text
NEGOTIATE
    │
    └── STATUS_SUCCESS
            │
            ▼
SESSION_SETUP_ANDX
    │
    └── STATUS_ACCESS_DENIED
```

# 9. Extraction of the SMB UID

The SMB1 header is 32 bytes long.

However, the `recv()` buffer begins with a four-byte NetBIOS Session Service header.

Therefore:

```text
recv buffer + 0x04 = SMB header
```

Within the SMB header, the UID field is located at offset `0x1C`.

Consequently:

```text
recv buffer + 0x04 + 0x1C
=
recv buffer + 0x20
```

The two bytes at:

```text
recv_buffer + 0x20
recv_buffer + 0x21
```

are therefore the SMB **UID (User ID)** field.

In the observed response these bytes are:

```text
00 00
```

Therefore:

```text
UID = 0x0000
```

This interpretation is directly consistent with the subsequent instructions:

```asm
00401A59  mov cl,byte ptr [esp+3C]
00401A5D  mov dl,byte ptr [esp+3D]
```

Given the stack layout used by the function, these locations correspond to:

```text
recv_buffer + 0x20
recv_buffer + 0x21
```

and therefore retrieve the two bytes of the SMB UID.



This is a key reverse-engineering finding because it establishes a direct data dependency:

```text
SMB Session Setup response
        │
        ▼
UID field
        │
        ▼
00 00
        │
        ▼
0x4017B0
```

---

# 10. Why the UID Matters for the Next SMB Request

The UID is part of the SMB1 session context.

In a successful SMB Session Setup, the server normally assigns/returns a UID that identifies the established user/session context. Subsequent SMB requests use this identifier to associate the request with that session.

In the observed execution, however:

```text
Session Setup status = STATUS_ACCESS_DENIED
UID                  = 0x0000
```

Therefore, **no valid authenticated SMB user context** was established during this exchange.

Nevertheless, `0x401980` continues execution and extracts the returned UID bytes.

The two bytes are passed to:

```text
0x004017B0
```

where they become part of the next SMB request.

This means that the third request is **response-dependent** rather than being a completely static SMB packet.

# 14. UID Substitution Experiment

The original execution produced the following SMB Session Setup state:

```
Session Setup response
        │
        ├── STATUS_ACCESS_DENIED
        │
        └── UID = 0x0000
                │
                ▼
          0x004017B0
                │
                ▼
       Tree Connect request
```

A `0x0000` UID is consistent with the absence of a successfully established SMB session in the observed exchange. However, this alone cannot be used to explain the subsequent connection reset.

To test whether the zero UID was the direct cause of the failure, the UID used by `0x004017B0` was manually replaced with `0x1122`.

The resulting request was correctly reconstructed and transmitted:

```
UID = 0x1122
send #3 = SUCCESS
```

Nevertheless, the subsequent `recv()` produced exactly the same failure:

```
EAX = 0xFFFFFFFF
```

followed by:

```
WSAGetLastError() = 0x2746
```

which corresponds to:

```
10054 / WSAECONNRESET
```

Therefore, the controlled UID substitution **doesnt change** the observed failure.

The most defensible conclusion is:

> The `0x0000` UID is an observable consequence of the failed Session Setup exchange, but the available dynamic evidence doesnt support identifying it as the direct cause of the Tree Connect connection reset.

This experiment is important because it eliminates a straightforward explanation for the failure without requiring speculation about the server-side implementation.

# 17. Dynamic Analysis Boundary of 0x00401980

At this point, the dynamic analysis of `0x00401980` is considered complete.

The controlled execution established the following sequence:

```
TCP connection to target:445
        │
        ▼
SMB_COM_NEGOTIATE
        │
        ▼
SMB_COM_SESSION_SETUP_ANDX
        │
        ├── STATUS_ACCESS_DENIED
        └── UID = 0x0000
        │
        ▼
SMB_COM_TREE_CONNECT_ANDX
        │
        ├── UID = 0x0000 → tested
        │
        └── UID = 0x1122 → tested
        │
        ▼
send() → SUCCESS
        │
        ▼
recv() → SOCKET_ERROR
        │
        ▼
WSAECONNRESET (10054)
        │
        ▼
closesocket()
        │
        ▼
return / failure path
```

The UID substitution experiment is particularly relevant because changing the UID from `0x0000` to `0x1122` didnt alter the outcome. Therefore, the dynamic evidence doest provide a reliable way to continue execution into the subsequent SMB transaction stage.

Further attempts to force the exchange past this point would require modifying additional protocol state or reproducing a valid server-side SMB session, which would no longer represent the naturally observed execution path of the sample.

For this reason, the remaining network logic of `0x00401980` will be analysed statically. The subsequent SMB transaction and named-pipe stages can be examined from the packet construction routines, control flow, API usage, and embedded data. Any interpretation of their role in the overall propagation mechanism will be explicitly presented as a **working hypothesis** unless supported by additional direct evidence.

This establishes a clear boundary between:

```
Dynamically verified behaviour
        │
        ▼
TCP/445 → SMB negotiation → Session Setup
→ Tree Connect → connection reset
```

and:

```
Statically identified behaviour
        │
        ▼
SMB_COM_TRANSACTION → \PIPE\ → subsequent logic
```

The latter can therefore be analysed theoretically without presenting unverified stages as dynamically observed execution.

# 18. Static Reconstruction of the Subsequent SMB Propagation Stage

The dynamic analysis of `0x00401980` couldnt be extended beyond the Tree Connect exchange. The third `recv()` returned `SOCKET_ERROR` with `WSAECONNRESET`, and replacing the `0x0000` UID with a controlled value (`0x1122`) didnt change the result. Therefore, the subsequent SMB stages couldnt be observed through a valid end-to-end dynamic execution in the controlled environment.

However, the remaining code path can still be reconstructed statically.

The next preconstructed packet is located at:

```text
0x0042E4F4
```

**Figure 11. `0x00401980` dump of send4 ()**
![](0x00401980%20Dump%20of%20send4%20().png)

[0x00401980 data of send4 () ](0x00401980%20data%20of%20send4%20()%20.txt) .

and begins with:

```text
00 00 00 4A
FF 53 4D 42
25
```

identifying an SMB1 `SMB_COM_TRANSACTION` request.

More importantly, its transaction setup contains:

```text
23 00 00 00
```

where `0x0023` corresponds to `TRANS_PEEK_NMPIPE`, with a file identifier of `0x0000`. The request also contains:

```text
07 00
5C 50 49 50 45 5C 00
```

corresponding to the `\PIPE\` path.

This is significant because the packet is not simply another generic SMB transaction. It represents a transaction directed at the SMB named-pipe mechanism through the IPC$ tree established by the preceding Tree Connect stage.

The packet can therefore be represented conceptually as:

```text
SMB_COM_TRANSACTION
        │
        ├── TRANS_PEEK_NMPIPE
        │
        ├── FID = 0x0000
        │
        └── \PIPE\
```

The code preceding the subsequent `send()` also patches the SMB header using selected bytes from the data structure associated with the preceding receive operation:

```text
source + 0x00 → TID
source + 0x01 → TID

source + 0x00 → PID
source + 0x01 → PID

source + 0x04 → UID
source + 0x05 → UID

source + 0x06 → MID low
source + 0x0B → MID high
```

Because the preceding `recv()` failed during the controlled execution, the actual runtime values of these fields couldnt be obtained. Nevertheless, the static data flow demonstrates that the subsequent transaction request is designed to use response-dependent SMB context rather than being an isolated packet.

The resulting logical sequence is therefore:

```text
SMB_COM_NEGOTIATE
        │
        ▼
SMB_COM_SESSION_SETUP_ANDX
        │
        ▼
SMB_COM_TREE_CONNECT_ANDX
        │
        ▼
       IPC$
        │
        ▼
SMB_COM_TRANSACTION
        │
        ├── TRANS_PEEK_NMPIPE
        ├── FID = 0x0000
        └── \PIPE\
```

This sequence is consistent with the SMB-based propagation mechanism publicly documented for WannaCry and with the protocol sequence used in MS17-010-related SMB exploitation research. WannaCry is documented as using the EternalBlue SMB vulnerability for network propagation, while the corresponding SMB exploitation workflow includes a `SMB_COM_TRANSACTION` / `TRANS_PEEK_NMPIPE` stage following Tree Connect.

Therefore, although the controlled environment didnt allow the final stages to be dynamically executed, the static analysis provides *strong evidence* that the network component proceeds beyond simple SMB connectivity and session establishment into a **named-pipe transaction stage associated with the SMB propagation mechanism**.

At this point, the analysis has reached the practical boundary of what can be reliably established from the available controlled execution. The exact server response and subsequent exploitation packets couldnt be observed because the Tree Connect exchange terminated with `WSAECONNRESET`. Further reconstruction would therefore require either a compatible vulnerable SMB target or additional external execution evidence.

For the purposes of this analysis, the remaining behaviour is treated as a **statically reconstructed propagation/exploitation stage rather than dynamically verified execution**.

This distinction is intentional: the analysis doesnt claim to have dynamically reproduced the complete WannaCry propagation chain, but it establishes the transition from local subnet discovery and TCP/445 scanning to SMB session establishment and, statically, to the `TRANS_PEEK_NMPIPE` named-pipe transaction used as part of the subsequent SMB exploitation workflow.
