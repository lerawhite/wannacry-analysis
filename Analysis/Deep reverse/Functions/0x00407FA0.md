As we recall, the logic for entering this block is that the _wannacry.exe_ process is running as the _mssecvc2.0_ service. Before `0x00407FA0`, the `OpenServiceA` function was called with _mssecvc2.0_ as the service name, where `handle = ESI = 0x00001414`. I patched this value because the service wasnt actually running in our analysis environment.

The value `0x3C` is an unknown argument at this stage. As determined later in the analysis, it represents a **delay value in seconds**.
![](0x00407FA0%20Argc%20of%20this%20function.png)


The `0x00407FA0` block isnt meaningful to analyze in Ghidra, as the arguments for the **ChangeServiceConfig2A** function are constructed dynamically on the stack and may involve obfuscation.

This is a signature of next called function:

```c
BOOL ChangeServiceConfig2A(
  SC_HANDLE hService,//Descriptor
  DWORD     dwInfoLevel, //What service do if he down
  LPVOID    lpInfo
);
```

And third argue is:

```c
typedef struct _SERVICE_FAILURE_ACTIONS {
  DWORD  dwResetPeriod;
  LPSTR  lpRebootMsg;
  LPSTR  lpCommand;
  DWORD  cActions;
  SC_ACTION *lpsaActions;
} SERVICE_FAILURE_ACTIONS;
```

```c
typedef struct _SC_ACTION {
  SC_ACTION_TYPE Type;
  DWORD          Delay;
} SC_ACTION;
```

type of actions:
```c
SC_ACTION_RESTART     // RESTART
SC_ACTION_RUN_COMMAND// RUN_COMMAND
SC_ACTION_REBOOT     // REBOOT  
```

What we see in **Figure 1** is the dynamic construction of the third argument (`lpInfo`) for the `ChangeServiceConfig2A` function. At this point, we need to determine:

- what the arguments passed to the `0x00407FA0` block are and what role they play;
- what is placed on the stack before the call to **ChangeServiceConfig2A**;
- how the _third argument_ is constructed and what its structure represents, in order to understand why the attacker uses this function.

Argue before call:
```asm
push ecx   ; lpInfo = 0x0019FE40 (stack)
push 2     ; SERVICE_CONFIG_FAILURE_ACTIONS
push edx   ; hService = 0x1414 (patched handle(OpenService(mssecvc2.0)))
call ChangeServiceConfig2A
```

```c
ChangeServiceConfig2A(
    0x1414,
    SERVICE_CONFIG_FAILURE_ACTIONS,
    0x0019FE40
);
```

## Research Report 


The malware configures service failure recovery using `ChangeServiceConfig2A` with `SERVICE_CONFIG_FAILURE_ACTIONS`.  
It sets a single recovery action:
 
- **Action**: Restart the service
 - **Delay**: 60 seconds
 
This ensures automatic recovery via SCM if the service is terminated.
